## 使用说明 · 面试官的心理模型

面试官问的每一句都在验证三件事之一：**这是不是你做的**、**你懂不懂为什么这么做**、**出了事你怎么办**。对应到你的项目：

| 面试官想验证 | 他会用什么问题刺探 | 你要给出的信号 |
|---|---|---|
| 是不是你做的 | "这个配置文件里 `function.definition` 为什么是这几项？" | 具体到文件、字段、数值、踩过的坑 |
| 懂不懂为什么 | "为什么不用分布式锁？为什么不用延迟消息？" | 说清**两个方案各自的代价**，再说选择的判据 |
| 出事怎么办 | "扣完库存服务挂了咋办？Redis 挂了咋办？" | 先给检测手段（怎么发现），再给补偿路径，最后给兜底 |
| 会不会过度设计 | "有必要搞责任链吗？Seata 是不是太重？" | 承认成本，给出"什么量级才值得"的判据 |

**三条话术纪律**：

1. **先给结论，再给理由，最后给代价。** "我用 Lua 扣减，因为它一次往返就完成幂等+判断+扣减；代价是 Lua 里不能做回滚，所以我把所有校验放在写操作之前。"——这三段缺一段，面试官就会追着问。
2. **不确定就说不确定，但要给出验证路径。** "这块我记不清具体数值，我的验证方式是看 `XXX` 配置 / 跑一次 `XXX`。"（面试官不怕你不会，怕你编。）
3. **永远准备一句"如果流量再大 10 倍"**。你的项目多数方案是为"千万级订单、几百 QPS"设计的，这个前提被追问时要能说出来，否则"为什么不全上最强方案"就答不上。

# 第 0 章 · 开场与自我介绍（追问你 10 分钟）

### Q0.1 请做个自我介绍，重点讲你最有把握的项目。🔴

**答（45–60 秒，别超）**：

> 我做的是一个 **NFT 数字藏品交易平台 NFTurbo**，技术栈是 Spring Cloud + Dubbo 微服务、15 个 Spring Boot 应用、Java 21。
>
> 我在里面负责的是**交易主链路**：用户认证、秒杀下单、订单与支付、库存。三个我自己做的、印象最深的设计：
> - **秒杀扣减**用 Redis Lua 把"幂等校验 + 库存判断 + 原子扣减 + 记流水"压成一次调用，绕开分布式锁的多轮往返，线上压测单机 300+ 并发不超卖；
> - **订单号**用"雪花 + 基因法"，订单号末 4 位编码买家 ID 的分片结果，带订单号或买家 ID 任一就能精准命中一张分表；
> - **一致性**上没有一把梭：下单走对账补偿、关单走事务消息、支付成功走 Seata AT、上链走事务钩子 + 定时重试，按场景选强度。

**追问 1：你为什么把"一致性按场景分层"当亮点？这不是承认你们方案不统一吗？**

**答**：统一方案的成本更高。秒杀要保可用性，用强一致会把下单 P99 拖上去；而上链是外部 HTTP 调用，绝不能放进事务里等着它。所以我的判据是**"这个环节失败了会造成什么后果"**——库存多扣会导致超卖资损，必须强；上链慢一点只是用户晚看到链上信息，可最终一致。

**追问 2：15 个 Spring Boot 应用部署在一个 Maven 工程里，生产上合理吗？**

**答**：项目本身是为省部署成本把多个启动类聚合在一个工程，**生产上应该拆成独立服务、独立库**。但拆不拆不影响我负责的那部分设计——Dubbo 调用、分片配置、事务边界都是按"独立服务"的假设写的。

**追问 3：你提到 QPS 300+，这个数字怎么来的？🔴**

**答**：是我自己用压测工具压秒杀接口得到的单机吞吐，单商品、2 台测试机。**这不是全链路压测，也不含支付链路**。如果要讲全链路，我只能说"下单侧我压过"，不夸大到整个系统。

---

### Q0.2 你在这个项目里最花时间的三件事是什么？

**答**：① 秒杀库存的正确性——从"加分布式锁 + 多次 Redis 操作"改成"单次 Lua"，中间花时间最多的是想清楚**幂等键怎么设计**（`DECREASE_<identifier>`）以及**Lua 出错后怎么让 Java 侧区分错误类型**；② 订单分库分表后**不带分片键的查询**怎么办——最后订单号带基因、卖家侧走 ES；③ 超时关单的扫表 SQL 打不动——加了逆序冗余字段和联合索引才把 `likeLeft` 变成 `likeRight`。

**追问：这三个里哪个是你独立定位出根因的？**

**答**：第三个。原 SQL 用买家 ID 尾号做分片条件，写的是 `likeLeft('%xx')`，等于 SQL 里对列做函数运算，索引必然失效，慢 SQL 到秒级。我通过 `explain` 看到 type=ALL（或范围扫描）确认，然后加 `reverse_buyer_id` 并把条件改成 `reverse_buyer_id like 'xx%'`，配合 `(reverse_buyer_id, order_state, gmt_create)` 联合索引命中。

# 第 1 章 · 项目全景与架构选型

### Q1.1 整体架构介绍下，为什么用微服务？🔴

**答**：自上而下是 **Gateway(:8081) → auth / admin / artist / business 三个业务集群 → 中间件**。业务集群里按领域切了 12 个子模块：user、inventory、order、pay、trade（编排）、goods（商品聚合，含 collection / box / star）、chain、synthesis、album、series、notice、app。

用微服务的理由是**业务边界天然清晰**：藏品、订单、支付、库存的关注点完全不同，库存要被"秒杀、合成、盲盒、转让"四个场景复用，独立成服务后调用方统一走 Dubbo 接口（`nft-turbo-api` 契约层），不用各写一份扣减逻辑。

**追问 1：这么多模块，一次下单会经过哪些模块？**

**答**：`trade` 是编排层 —— 用户请求打到 Gateway，鉴权通过后进 `trade`，trade 依次：① 校验（状态、库存、用户）；② 生成订单号；③ 调 `inventory` 用 Lua 预扣库存并记流水；④ 调 `order` 建单（分库分表）；⑤ 生成支付单返回支付链接。支付回调后进 `pay`，pay 再推进 `order` 状态、调 `chain` 上链。

**追问 2：为什么要有 trade 这一层？直接让 order 调 inventory 不行吗？**

**答**：trade 承担**跨领域的编排职责**（Sequential 风格）——一次下单要动库存和订单两个领域，如果 order 直接依赖 inventory，订单域就被库存域绑死了；反过来让 inventory 依赖 order 更荒谬。trade 作为编排层只依赖双方的接口，符合依赖倒置。

**追问 3：模块之间用什么通信？为什么不用 HTTP？🔴**

**答**：Dubbo（RPC），走 `nft-turbo-api` 里定义的接口契约。选 Dubbo 而不是 OpenFeign 的理由：① 内部服务调用是**长连接 + 二进制序列化**，没有 HTTP 的头部冗余和 JSON 文本开销；② Dubbo 自带服务发现（接 Nacos）、负载均衡、熔断，Spring Cloud 侧还要额外引 LoadBalancer / CircuitBreaker；③ 团队既有技术栈。

**代价我要说清楚**：Dubbo 的接口变更要同步更新契约包并重新发布 provider/consumer，不像 HTTP 那样可以单独先发一方；而且跨语言能力比 REST 弱。

**追问 4：Dubbo 和 HTTP 的本质区别是什么？**

**答**：**HTTP 是协议，Dubbo 是 RPC 框架（默认走 TCP 私有协议）**。HTTP 是无状态的应用层协议，任何语⾔、任何工具都能调，天然可跨语言、可被网关/浏览器直连；RPC 更关注"像调本地方法一样调远程"，用长连接、二进制序列化、接口级契约换性能和开发体验。
一句话：**HTTP 赢在通用性，RPC 赢在内部调用性能与治理能力**。对外暴露接口仍然走 HTTP（Gateway 之后是 REST），内部服务间用 Dubbo。

**追问 5：那 Gateway 为什么还要 LoadBalancer？Dubbo 不是也能负载均衡吗？**

**答**：层级不同。Gateway 均衡的是**外部 HTTP 请求 → 后端服务的入口**（走 Spring Cloud LoadBalancer）；Dubbo 均衡的是**服务之间的 RPC 调用**。两者都基于 Nacos 的服务发现，但作用在链路的不同段。

### Q1.2 Nacos 在项目里起了什么作用？

**答**：两个作用。① **服务注册与发现**：Gateway 的服务列表、Dubbo 的 provider 地址都从 Nacos 拿；② **配置中心**：`application.yml` 通过 `spring.config.import` 合并 Nacos 上的公共配置。

**追问 1：Nacos 挂了会怎样？**

**答**：**已启动的服务不会立刻挂** —— 客户端本地有服务列表缓存，配置也有本地快照。影响是：新的服务实例注册不上、配置变更下不去、消费者感知不到 provider 上下线（会继续往已下线的节点发请求直到本地缓存过期/健康检查剔除）。所以生产上 Nacos 要集群部署（3 节点）并持久化到 MySQL。

**追问 2：Nacos 配置和本地 `application.yml` 冲突谁优先？**

**答**：Nacos 的**优先级更高**（`spring.config.import` 引入的配置默认覆盖本地 `application.yml`）——这是你项目里真实踩过的坑类型：本地改了没生效，因为 Nacos 上的值盖住了。

### Q1.3 项目里用到了哪些设计模式？

**答**：四个用得最实的：

| 模式 | 落地位置 | 解决的问题 |
|---|---|---|
| **责任链** | 下单/合成的前置校验器链 | 校验项可插拔、顺序可控、单个校验器职责单一 |
| **工厂 + 策略** | `ChainServiceFactory` 按 `ChainType` 选 `WenChangChainServiceImpl` / `MockChainServiceImpl`；支付方式选支付策略 | 新增渠道只加一个实现类，不改调用方 |
| **模板方法** | `AbstractChainService` 定义"建账户 / 铸造 / 转让"的骨架，子类实现差异步骤；`AbstractInventoryRedisService` 同为骨架 | 公共流程上提，差异下放 |
| **建造者** | 复杂请求对象组装 | 参数多、可选参数多 |

**追问 1：责任链有必要吗？几个 if-else 不行吗？🔴**

**答**：**校验项少的时候 if-else 更简单**。我用责任链的判据是：① 校验项会持续增加（藏品状态、用户实名、限购、库存、活动时间……）；② 每项校验需要独立单测；③ 不同场景要复用不同子集（秒杀走的校验和普通购买不一样）。
**责任链的代价**：链路对调用方不透明、调试要按节点排查、容易忘记 `if (!result.isSuccess()) return` 导致继续往下走——我就踩过后一个，表现为"校验不通过却建了单"，最后靠日志定位。折中做法是链只放**无副作用的纯校验**，涉及扣减的步骤绝不放进链里。

**追问 2：责任链怎么实现的？**

**答**：抽象 `Validator` 定义 `validate(context)`，每个实现类声明自己关心的校验项；用 Spring 收集同类型 Bean 组成有序列表，或者显式声明 `next` 指针。串行执行，任一失败即中断返回。

### Q1.4 线上问题排查过哪些？🔴

**答**：三个典型的，都可以讲根因和定位过程：

1. **事务监听器不触发**：调下单接口，`InventoryDecreaseTransactionListener` 的断点永远不命中。根因是**Spring Boot 多模块配置覆盖**——`nft-turbo-app` 的 `application.yml` 里 `spring.cloud.function.definition` 覆盖了 `nft-turbo-trade` 模块的定义，导致 `newBuy-out-0` 的事务生产者配置没生效，`StreamBridge` 发出去的是**普通消息而不是事务消息**，所以本地事务回调和回查根本不会被调用。定位方式是从发送端 `StreamProducer.send()` 一路追到 `StreamBridge`，再看绑定配置有没有被加载。修复是把必要配置直接写进主应用 yml，并把 `function.definition` 精简为只保留真的有 Consumer bean 的函数（`orderClose`）。
   → **这个坑的通用教训**：主应用的 yml 优先级高于依赖模块，多模块项目里"配置写了但没生效"要第一时间怀疑覆盖。

2. **事务消息发送报 `No route info of this topic`**：RocketMQ 的 broker 用 `-n 127.0.0.1:9876` 启动，指向的是**容器自己**，而 namesrv 在另一个容器里，broker 根本注册不上；同时 namesrv 也用 `-n 127.0.0.1:9876` 只监听了 lo 接口，宿主机的端口映射转发不进去。改成 `-n namesrv:9876`（Docker 服务名）后恢复，另外事务消息的 topic 不会自动创建，要 `mqadmin updateTopic` 手动建。

3. **订单详情页倒计时显示 `NaN:NaN`**：后端 `payExpireTime` 是 `java.util.Date`，Spring Boot 3 默认 Jackson 序列化成 ISO 8601 字符串 `"2026-06-27T06:55:49.000+00:00"`，前端直接拿字符串减时间戳得到 `NaN`，而且 `NaN <= 0` 为 false，原有的兜底判断也拦不住。前端统一 `new Date(target).getTime()` 转毫秒。

**追问：这三个里哪个最像"你的锅"？**

**答**：第 1 个和第 3 个都是我自己代码/配置的问题。第 1 个的教训是我当时以为"配置在依赖模块里写了就生效"，没有在应用启动后打印实际的绑定配置去核对；后来我的习惯是**关键 MQ 绑定启动时打一行日志确认 producerType 是不是 Trans**。

# 第 2 章 · 用户与认证模块

> 用户模块是 `面试题.md` 里被问得最密的模块（几乎每场面试都从注册登录开刀）。核心链路：**注册（验证码 + 限流 + 分布式锁 + 布隆过滤器 + 邀请绑定 + 排行榜）→ 登录（Sa-Token 发 token）→ 实名认证（第三方 + 加密存储）→ 缓存一致性**。

### Q2.1 用户模块有哪些功能？

**答**：注册、登录、退出、头像/昵称修改、实名认证、邀请码与邀请排行榜、链账户创建（区块链侧的身份）。

**追问：数藏项目的用户和普通电商用户有什么区别？🔴**

**答**：三点本质差异：
1. **强实名**：数藏涉及数字资产，必须实名认证（姓名 + 身份证）才能交易，普通电商不强制；
2. **有链上身份**：用户要创建链账户（钱包地址），资产是链上确权的，不是数据库里一行记录；
3. **"持有凭证"的定义不同**：普通电商"我的订单"就是持有关系；数藏里"持有藏品"是独立的持有记录（`held_collection`），并且有独立的状态机（铸造中 → 成功 → 已销毁/已转让）。

**追问：怎么证明一个用户真的持有这个藏品？**

**答**：不能只信数据库。有两条证据链：① 库里 `held_collection` 表的持有记录（状态为 SUCCEED、owner 是当前用户）；② 链上该藏品 tokenId 的所有者地址对应用户的链账户。业务上用前者做快速判定，后者做对账和纠纷裁决。

### Q2.2 注册流程讲一下。🔴

**答**：五步：
1. **发验证码**：先经**滑动窗口限流**（同手机号单位时间只能发 N 次），再加**分布式锁**防止并发重复发，然后生成随机验证码写 Redis（5 分钟过期），最后调短信服务发出去；
2. **用户提交**：手机号 + 验证码 + 密码（+ 可选邀请码）；
3. **校验验证码**：比对 Redis，比对成功**删除**（防止一码多用）；
4. **分配昵称和邀请码**：昵称固定前缀 + 随机数字，用**布隆过滤器**判重（昵称、邀请码各一个），重复则重试；
5. **落库 + 绑邀请关系**：写用户表（手机号、昵称、状态、邀请码、邀请人 ID），并给邀请人的 **ZSET 排行榜**加分。

**追问 1：验证码怎么生成、存哪、存多久？**

**答**：随机数（项目里用的是随机字符串），存 Redis，**5 分钟过期**。校验时"取值比对 + 删除"，注意**校验和删除要保证原子性**，否则并发下同一个验证码可能被用两次——这一点可以用 Lua 或 `getdel`。

**追问 2：5 分钟内用户点了两次"获取验证码"怎么办？🔴**

**答**：分两种情况。
- **防刷视角**：滑动窗口限流会拦住超出频率的请求（超过阈值直接拒绝）；
- **用户体验视角**：如果用户在有效期内重复请求，两种策略——① 直接拒绝并提示"验证码已发送"；② 生成新验证码覆盖旧的，**旧验证码立即失效**。

我项目里走的是"覆盖 + 旧码失效"路线：**同一手机号只保留最新一个验证码**，避免用户收到两条短信后分不清哪条有效。

**追问 3：为什么是"滑动窗口 + 分布式锁"两个都要？有了滑动窗口为什么还要锁？🔴**

**答**：**它们防的是不同东西，不是重复手段**。
- 滑动窗口限流防的是"**单位时间内次数超限**"（比如 1 分钟 3 次）——它是**频次**控制，属于业务规则；
- 分布式锁防的是"**同一瞬间的并发请求同时通过**"——限流算法本身在"判断 + 计数写入"之间如果不原子，两个请求可能同时读到计数 2 然后都判定通过（**限流被击穿**），这时候临界区需要锁来串行化。

所以顺序是：先限流做粗筛，再用锁保证"生成验证码 + 发短信 + 写缓存"这段临界区串行。

**追问 4：并发情况下滑动窗口会被击穿吗？**

**答**：会，如果"读计数、判断、写计数"不是原子的。我的实现是 **ZSET 滑动窗口**——`zremrangeByScore` 清窗口外、`zcard` 取窗口内数量、`zadd` 写入当前请求。这三步如果不放在一个 Lua 脚本里，并发下会出现**多算**（都看到旧计数）。所以正确实现在窗口计数这一步必须是 Lua 或 Redisson 的 `RRateLimiter` 之类原子实现。加了分布式锁是更保守的做法，代价是 QPS 被锁的吞吐限制住。

**追问 5：限流的算法有哪些？你用的滑动窗口和它们什么区别？**

**答**：

| 算法 | 原理 | 缺点 |
|---|---|---|
| 固定窗口 | 按分钟/秒切分计数，超了拒绝 | **临界问题**：窗口边界两侧各打满一次，实际瞬时流量是 2 倍阈值 |
| 滑动窗口 | 用 ZSET 记录请求时间戳，统计"最近 N 秒"内的量 | 内存随请求量增长；要原子实现 |
| 令牌桶 | 匀速产令牌，桶有容量、允许突发 | 需要维护令牌产生速率与桶 |
| 漏桶 | 请求先进队列，匀速流出 | 不允许突发，延迟高 |

我的滑动窗口用 **ZSET**：score 是时间戳，value 是唯一标识（如 UUID），这样既精确又天然有序。

### Q2.3 用户昵称怎么生成的？用户名能重复吗？怎么避免？🔴

**答**：昵称 = **固定前缀 + 随机数字**（比如 `用户839201`）。**不允许重复**——但为了避开"每次都要查库"的开销，用**布隆过滤器**做前置判重：生成候选昵称 → 布隆过滤器 `contains` 判断"可能存在" → 若可能存在再走 DB 唯一索引兜底 → 插入成功后把昵称 `add` 进布隆过滤器。

**追问 1：布隆过滤器为什么能判重？原理是什么？**

**答**：它用**一个位数组 + k 个哈希函数**。写入时对元素做 k 次哈希，把对应 k 个 bit 置 1；查询时同样哈希，若有一位是 0 说明**一定不存在**，若全是 1 说明**可能存在**。
特性：**说不存在一定准，说存在可能误判**；**删不掉元素**（多个元素共享 bit，删了会影响别人）；空间效率极高（10 万容量、1% 误判率大概只需要十几万 bit）。

**追问 2：底层是什么数据结构？普通的 hash 表吗？🔴**

**答**：**不是 hash 表，是位数组（bit array）**。这点常被考：hash 表存的是"元素本体或指针"，布隆过滤器只存"若干个 bit 的状态"，所以它能用极小的空间表达极大的集合，代价是误判和不可删除。
Redisson 的实现 `RBloomFilter` 用的是 Redis 的 **String（位图）**，通过 `setbit/getbit` 操作。

**追问 3：误判怎么办？判断"可能重复"之后呢？**

**答**：误判只是**多查一次数据库**，不影响正确性。最终唯一性由**数据库唯一索引**保证——布隆过滤器的作用是"挡掉绝大多数必然不重复的请求"，而不是代替唯一约束。

**追问 4：为什么不直接查数据库？**

**答**：注册和昵称修改是**高频**操作，每次生成昵称都要 `select ... where nickname = ?`，随着表变大索引查询成本上升；而且这类查询基本都是"不存在"的结果，等于每次都白扫。布隆过滤器在内存/Redis 里做一次位运算就能挡掉 99% 的无意义查询。**代价是引入误判和"删除困难"**——所以昵称一旦注册就不该被"释放回池子"。

**追问 5：那用户改名了，旧的昵称是不是还占着？**

**答**：是。布隆过滤器不能删除，这是它的固有代价。项目里昵称不允许改名（或改名走独立流程），就是为了绕开这个问题。

### Q2.4 邀请码怎么保证唯一？邀请排行榜怎么做的？🔴

**答**：
- **邀请码唯一性**：同昵称 —— 随机生成 → 布隆过滤器（`inviteCodeBloomFilter`，10 万 / 0.01）判重 → DB 唯一索引兜底 → 成功后写入过滤器（`UserService.java:177/204`）。
- **排行榜**：Redis **ZSET**，member 是用户 ID，score 是邀请人数。查询 Top N 用 `entryRangeReversed(0, N-1)`（倒序取），查某个用户的排名用 `revRank(userId)`（`UserService.java:391/413`）。
  **一个细节**：score 存的是 `邀请数 × 100`（`UserService.java:401` 显示取出来要 `/100`），乘 100 是为了**留出小数位做同分时的次级排序**（比如小数点后放最后邀请时间戳），避免同分用户的排名随机抖动。

**追问 1：排行榜什么时候更新？数据库里有没有维护排名？**

**答**：**实时更新**——用户注册绑定邀请关系时同步 `zincrby` 给邀请人加分。**数据库不维护排名**，只在用户表存"邀请人 ID"这一条事实关系；排行榜完全是 Redis 派生出来的视图。

**追问 2：那 Redis 挂了，排行榜数据不就丢了？🔴**

**答**：**排行榜丢得起，邀请关系不能丢**。设计上是"事实存 DB（邀请人 ID 关联）、榜单存 Redis"。Redis 挂了榜单为空，可以用一条**离线任务扫用户表 group by 邀请人 ID** 把 ZSET 重建出来；重建期间榜单降级展示或提示"榜单一小时后再来"。
这就是为什么"邀请关系"必须落库——**派生数据可以重建，事实数据不行**。

**追问 3：ZSET 的底层是什么？为什么用跳表？**

**答**：ZSET 有两种编码：**元素少且短 → ziplist（listpack），元素多或长 → skiplist + hash 表**。跳表负责按 score 有序，hash 表负责 member → score 的 O(1) 查找。
用跳表而不是平衡树的原因：① 范围查询天然友好（跳表就是有序链表加多级索引）；② **实现简单**，插入删除只需要改指针、不用旋转重平衡；③ 并发/内存友好。

**追问 4：跳表查询的时间复杂度？**

**答**：期望 **O(log N)**。每一层大约每隔一个节点抽一个上层索引，层数期望 O(log N)，查找从最高层往下逐层逼近。

### Q2.5 验证码登录/账号密码登录怎么实现的？登录后用户信息存在哪？🔴

**答**：登录支持**验证码 + 密码**两种。登录成功后用 **Sa-Token** 发 token：把 token 和登录态写进 Redis，token 返回给前端。**接口层的鉴权在 Gateway 完成**——不是每个业务服务自己校验，而是网关统一拦截（`SaReactorFilter`），校验通过后把用户信息透传给下游。

**追问 1：网关怎么知道这个 token 是谁的？**

**答**：Sa-Token 的 token 本身是一个随机串，服务端（Redis）存 `token → 登录 ID` 的映射以及权限信息。网关拿到 token 后查 Redis 得到当前登录用户，再根据路由规则做角色/权限校验（`StpInterfaceImpl` 动态返回角色 `ADMIN/CUSTOMER` 和权限 `BASIC/AUTH/FROZEN`）。

**追问 2：为什么在网关做统一鉴权，而不是每个服务自己验？**

**答**：① 避免每个服务重复引入认证逻辑和依赖；② 一致性强，不会出现某个服务漏配；③ 网关是流量的唯一入口，天然适合做这道关。
**代价**：网关成为单点，它挂了所有业务都进不来（所以网关要集群）；另外"绕过网关直连服务端口"是必须封死的（内网部署 + 服务不对外暴露端口）。

**追问 3：为什么用 Sa-Token 不用 Spring Security / OAuth2？**

**答**：项目是"网关统一鉴权 + 简单角色权限"的场景，Sa-Token 的 API 更直观（`checkRole` / `checkPermission` / 排除列表），接入成本低。Spring Security 的过滤器链和 OAuth2 的授权码流程更适合"第三方接入 + 精细的资源服务器"场景，对这个项目是过度设计。**要能说清代价**：Spring Security 生态更完整、和标准协议贴合，换成"对外提供 OpenAPI 给第三方"时 Sa-Token 就不够了。

**追问 4：token 在 Redis 里怎么存的？过期时间多久？**

**答**：`Sa-Token` 的会话存储，30 分钟级别的滑动过期（每次访问续期）。另外项目里还有一类**防重复提交 token**（见 Q4.6），那是另一套，别混为一谈——面试时如果面试官问"token 存多久"，先反问一句"您说的是登录 token 还是防重 token"，这一问能立刻拉开层次。

### Q2.6 实名认证怎么实现的？姓名和身份证号怎么存的？日志有脱敏吗？🔴

**答**：
- **实现**：调第三方接口做"姓名 + 身份证号"二要素核验，返回是否一致；
- **存储**：**不明文存**。用自定义 `TypeHandler` 在 MyBatis 读写时自动加解密——写库前加密、读取时解密，业务代码无感知；
- **脱敏**：日志侧用类似 `SensitiveLogback` 的脱敏能力，输出时把身份证号打码（保留前 6 后 4 之类）。

**追问 1：明文传给第三方吗？**

**答**：**传输必须是 HTTPS**，这是底线；"是否能避免明文出入参"取决于第三方接口契约——二要素核验的本质就是要比对明文，所以请求体里是明文但走加密信道。**要在回答里说清"传输加密 ≠ 存储加密 ≠ 展示脱敏"是三件事**。

**追问 2：为什么不存明文？加密之后怎么查？**

**答**：因为身份证号属于**个人敏感信息**，明文存储一旦库被拖走就是重大事故，合规上也不允许。代价是**不能对密文做等值查询**（除非用确定性加密，但确定性加密又弱化了安全性）。
所以业务设计上要避免"按身份证查用户"这种需求——如果需要查询，做法是**额外存一个不可逆的哈希列**（加固定盐）专门用于等值查询，加密列只用于展示端解密。

**追问 3：TypeHandler 是怎么工作的？**

**答**：MyBatis 在设置参数（`setParameter`）和取结果（`getResult`）时，会根据 Java 类型和 JDBC 类型找对应的 `TypeHandler`。我自定义的 handler 在写库前调加解密组件处理字段值，读出来时解密。这样**加解密逻辑收敛在一处**，不用在每个 Service 里手写。

**追问 4：用数据库工具直接查这条记录，看到的是什么？🔴**

**答**：看到的是**密文**（Base64/十六进制串）。这是"存储加密"的正常表现——正因如此，如果 DBA 或者别人拿到连接串直接查，也拿不到明文。这也回答了面试官真正想问的："你怎么证明你不是明文存的？"→ **演示一次数据库直查，看到密文，就是证据**。

### Q2.7 用户模块用到了缓存吗？缓存和数据库一致性怎么保证？🔴

**答**：用了**多级缓存**（JetCache 统一封装 Caffeine + Redis），用户信息读多写少，很适合缓存。

一致性策略是 **Cache Aside + 先更新数据库再删缓存**：
1. 写请求：先更新 DB，再删除缓存；
2. 读请求：缓存未命中 → 查 DB → 回填缓存。

**追问 1：为什么是"删除缓存"而不是"更新缓存"？**

**答**：更新缓存有两个问题：① **并发写**下两个请求的更新顺序可能和 DB 落库顺序不一致，导致缓存里留下旧值；② 如果这个缓存值是由多张表拼出来的，写一方未必知道怎么拼。删除是"让缓存失效"，下次读自然回源，**把复杂性交给读路径**。

**追问 2：为什么不是"先删缓存再更新 DB"？**

**答**：因为会出现经典的不一致窗口：A 删缓存 → B 读（未命中）→ B 读到**旧值**回填 → A 才更新 DB。结果是缓存里长期是旧值。
先更新 DB 再删缓存，虽然理论上也有窗口（读请求恰好在"更新 DB 后、删缓存前"回填了旧值），但那个窗口要求"读请求先于写请求到达数据库"，概率远低。

**追问 3：那删缓存失败了怎么办？🔴**

**答**：三步兜底：
1. **重试**：删除失败直接重试几次（本地重试或投递到 MQ 异步重试）；
2. **延迟双删**：更新 DB → 删缓存 → 延迟一段时间（比如 500ms~2s）**再删一次**，把并发窗口期可能被回填的旧值清掉；项目里冻结/解冻场景用的就是这个；
3. **兜底 TTL**：缓存本身设过期时间（本地 10 分钟、远程 60 分钟，且有 50 分钟的定时刷新），最坏情况是"不一致持续到过期"，而不是永久不一致。

**追问 4：JetCache 的 `@CacheRefresh` 是干什么的？**

**答**：它是**定时刷新**——在过期之前主动去刷新数据，避免"过期瞬间大量请求同时回源"（缓存击穿）。代价是**每次都真的查一次库**，所以适合"读多写少、能容忍短暂旧值"的数据（藏品、用户就是这样）。

**追问 5：本项目用户缓存具体怎么配的？**

**答**：`@Cached(name=":user:cache:id:", cacheType=BOTH)` + `@CacheRefresh(refresh=60min)`（`UserService.java:104-105`），即本地 + 远程双缓存，每 60 分钟刷新一次。藏品是本地 10 分钟、远程 60 分钟、50 分钟刷新（`BaseCollectionService.java:317-318`）。

### Q2.8 自定义分布式锁注解是怎么实现的？

**答**：三个组件：
1. **注解** `@DistributeLock`，参数包含 `scene`（业务场景）、`key`（SpEL 表达式，从方法参数里取锁的维度）、等待时间、超时时间；
2. **AOP 切面**：拦截注解，解析 SpEL 得到锁 key（如 `ORDER_CREATE + userId`），调用 Redisson 加锁，`try-finally` 里释放；
3. **Redisson** 作为锁实现（底层 Redis Hash + Lua 保证原子性 + 看门狗续期）。

**追问 1：为什么 `key` 要用 SpEL 表达式，而不是直接给字符串？**

**答**：锁的粒度要**按业务参数动态决定**。同一个方法，不同用户/不同订单要能并行，所以锁 key 必须包含参数——`#request.userId` 这样的表达式在运行时解析成实际的 key。如果写死字符串，就变成全局串行，性能直接崩。

**追问 2：Redisson 的 `lock` 和 `tryLock` 有什么区别？🔴**

**答**：
- `lock()`：**无限等待**直到拿到锁（拿不到就阻塞）；
- `tryLock(waitTime, leaseTime, unit)`：**最多等 waitTime**，等不到返回 false；`leaseTime` 指定持锁时间，`-1` 表示启用**看门狗自动续期**。

我用 `tryLock` 为主：**秒杀和下单这类接口不能让线程无限阻塞**——线程池被阻塞住会引发连锁雪崩（Tomcat/业务线程池打满）。超时拿不到锁就应该快速失败，返回"请稍后再试"。

**追问 3：看门狗续期的原理？**

**答**：Redisson 加锁时不指定 leaseTime（默认 30 秒）会启动一个后台定时任务，**每 1/3 租期（10 秒）检查一次业务是否还在执行**，是的话把锁的过期时间重置为 30 秒，直到业务结束主动释放。这样避免"业务没跑完锁就到期被别人抢走"。
**注意坑**：**指定了 leaseTime 就没有看门狗**——锁到点直接释放，长业务会被别的线程进来。

**追问 4：Redisson 怎么避免 A 线程把 B 线程的锁解掉？**

**答**：锁的 value 里存 **客户端唯一标识（UUID）+ 线程 ID**。解锁时用 Lua 脚本"先比较 value 是否是自己，一致才删除"——比较和删除在一次 Lua 里完成，保证原子性。如果发现锁不是自己的，直接返回不解。

**追问 5：不用 Redisson，还有别的方案吗？🔴**

**答**：三种，各有代价：

| 方案 | 实现 | 代价 |
|---|---|---|
| Redis `setnx` + 过期时间 | `SET key value NX PX 30000` 一把设置 | **释放锁需要 Lua 比较删除**；**续期要自己写**；主从切换时可能丢锁（异步复制） |
| 数据库 | `select ... for update` 行锁，或用唯一索引插入/删除模拟锁 | 性能差、连接占用高；`for update` 必须在事务里、要命中索引否则锁表 |
| ZooKeeper | 临时顺序节点 + watch | 强一致、能避免"锁丢失"，但引入新组件、性能低于 Redis |

**关键点**：`setnx` 单独用是不完整的，必须 `SET NX PX`（原子设置值和过期），否则"设置 key"和"设置过期"之间宕机就产生**死锁**。

**追问 6：`set` / `setnx` / `setex` 的区别？**

**答**：`setnx` 只在 key 不存在时设置，没有过期；`setex` 是设置值 + 过期（key 存在会覆盖）；`set k v NX PX ms` 是 `set` 命令的扩展参数，能**一次原子地完成"不存在才设置 + 带过期时间"**，是分布式锁的正确用法。
`setnx` + `expire` 两步的致命问题是**中间宕机 → 永不过期的死锁**。

**追问 7：想用数据库实现分布式锁怎么做？哪里见过？🔴**

**答**：两种：① `select ... for update` 借助 InnoDB 行锁（必须在事务中，且 `where` 条件要命中索引，否则升级成表锁）；② 用**唯一索引**——插入一条锁记录成功即获锁，删除即释放，冲突则插入失败。
**我项目里真的见过**：XXL-Job 的调度用的是**数据库锁**而不是 Redis 锁，因为它的场景是"低频、强一致、不能丢任务"——调度一次失败或重复调度的代价比性能损失大得多。Redis 锁在极端情况下（主从切换）有丢锁风险，对定时任务是不可接受的。

# 第 3 章 · 秒杀与库存（主战场）

> 这一章是整个面试含金量最高的一段。面试官会从"下单流程"一层层往下钻到 Lua 的每一行、MQ 的每一种失败、数据库的每一个索引。**建议这一章的答案全部背熟。**

### Q3.1 秒杀下单的流程完整讲一遍。🔴

**答**：分**同步**和**异步**两段：

**同步段（快，只做"抢到名额"）**：
1. 前置校验：藏品状态是否上架、用户是否实名/是否限购、活动时间；
2. **防重**：校验一次性 token（防按钮重复点击）；
3. 生成订单号（雪花 + 基因法）；
4. **Redis Lua 原子扣减**：一次调用完成"幂等校验 + 库存判断 + 扣减 + 记流水"；失败直接返回"库存不足"；
5. 扣减成功后，发送 **RocketMQ 事务消息**（`newBuy-out-0`），事务监听器在本地事务里做后续动作；
6. 返回用户"排队中/下单中"。

**异步段（慢，落地数据）**：
7. 消费者收到消息后，DB 侧扣减库存（`UPDATE ... WHERE saleable_inventory >= #{quantity}`），创建订单；
8. 消费端**幂等去重**（用订单号/流水号作为幂等键），重复消息直接 ACK。

**追问 1：为什么下单要拆成"同步扣 Redis + 异步建单"？🔴**

**答**：因为**建单是重操作**——要写订单表（分库分表路由）、更新库存表、还要走后续流程。同步做完，接口 RT 会随着流量上来迅速劣化，而且这些操作会把数据库连接占满。
拆开之后：同步段只碰 Redis（内存操作，微秒级），**先给用户一个确定的"抢到了"的信号**；异步段用 MQ 削峰，把瞬时洪峰摊平到数据库能承受的速率——这就是"削峰填谷"。

**追问 2：那用户看到的"下单成功"是真的成功吗？**

**答**：诚实说：**返回值是"抢到了名额"，最终下单结果靠轮询/推送**。这里要主动承认设计取舍——**用"最终一致"换吞吐**。如果业务不能接受（比如要立即返回订单号），那就得同步建单，代价是接口 RT。

**追问 3：先扣库存还是先创建订单？🔴**

**答**：**先扣库存**。理由：① 库存是稀缺资源，先扣能快速失败，不让超卖的请求进入建单流程；② 反过来先建单再扣库存，扣失败时要回滚订单，产生了"脏订单"和额外的补偿逻辑。
**追问会接着问**："那扣完库存建单失败了怎么办？" → 见 Q3.6（补偿回滚）。

**追问 4：异步链路里为什么要用事务消息，不是普通消息？🔴**

**答**：因为"发消息"和"本地事务"必须是原子的。用普通消息会出现两种情况：① 本地事务提交了但消息没发出去 → 库存扣了没建单；② 消息发出去了但本地事务回滚了 → 建了单没扣库存。
**事务消息**把这两者绑成半事务：先发 half 消息 → 执行本地事务 → 提交/回滚消息；**如果 commit 消息时宕机，Broker 会回查生产者的本地事务状态**，根据状态决定投递还是丢弃。这样保证"本地事务成功 ⇔ 消息一定被投递"。

### Q3.2 Redis Lua 脚本具体做了什么？为什么用 Lua 不用分布式锁？🔴

**答**：脚本一次执行完成四件事：
1. **幂等校验**：`hexists KEYS[2] ARGV[2]`——流水哈希里已经有这次操作的键就直接返回 `OPERATION_ALREADY_EXECUTED`；
2. **库存 key 存在性 + 数值校验**；
3. **库存判断**：为 0 返回 `INVENTORY_IS_ZERO`，不足返回 `INVENTORY_NOT_ENOUGH`；
4. **原子扣减 + 记流水**：`set` 新库存，`hset` 一条 JSON 流水（含 action/from/to/change/by/timestamp），**时间戳取自 Redis 服务器的 `time` 命令**而不是应用服务器。

**为什么不用分布式锁**：如果用锁，一次扣减需要 **4 次以上 Redis 往返**（加锁 → 读库存 → 判断 → 扣减 → 解锁），而**Redis 执行命令本身是单线程的**——把"判断 + 扣减"放进一个 Lua 脚本，Redis 会把它当**一个命令**串行执行，中间不会插入其他客户端的命令。**单线程的串行化本身就是锁**，再加一把锁是多此一举，还多了网络往返和锁失效的风险。

**追问 1：Lua 脚本的原子性到底指什么？能达到"要么都成功要么都失败"吗？🔴**

**答**：这是最容易答错的一题，必须说准：
- Redis 执行 Lua 时**不会被其他命令打断**（原子性 = 隔离性，像一个小事务），这是"不可中断"；
- 但 **Lua 脚本不具备回滚能力**。如果脚本执行到一半报错（比如类型错误、对 string 做 `incr`），**已经执行的写命令不会撤销**。

**所以我的脚本是"把校验全部放在写操作之前"**：幂等校验 → key 校验 → 数值校验 → 库存充足校验，全部通过后才执行 `set` + `hset`。这样脚本只要执行到写，前面就一定没有失败点；如果校验失败，是在**没有任何写操作**的情况下用 `redis.error_reply` 返回错误码。这就是"没有回滚能力也能保证一致性"的原因。

**追问 2：如果 `set` 成功但 `hset` 失败呢？**

**答**：理论上 Lua 内部两条命令之间不会因为网络失败——它们是同一个请求内的顺序执行。真正会失败的是**类型错误之类的运行时错误**，而这种错误在写之前的校验阶段就该被发现。另外工程上的兜底是**流水只用于对账和幂等判断**，即使流水缺失，DB 侧的库存扣减也是以数据库为准的（见 Q3.4），不会因为流水丢了一条就超卖。

**追问 3：失败怎么返回给 Java？**

**答**：用 `redis.error_reply('错误码')`，Redisson 侧会抛 `RedisException`，Java catch 之后按 `e.getMessage().startsWith(...)` 区分错误码，转成业务响应（`INVENTORY_NOT_ENOUGH` / `INVENTORY_IS_ZERO` / `KEY_NOT_FOUND` / `OPERATION_ALREADY_EXECUTED`）。
注意 `OPERATION_ALREADY_EXECUTED` 是**幂等命中**，代码里把它当成功返回（`success=true`），因为它意味着"这次操作之前已经成功过了"。

**追问 4：幂等键（流水 key）怎么来的？会不会重复？🔴**

**答**：幂等键是 `DECREASE_<identifier>`，`identifier` 是**一次下单的唯一标识**——项目里用的是**详情页拿到的一次性 token**（防重 token），它本身就是"一次下单意图"的凭证。
会不会重复？① token 生成用的是 UUID/雪花类唯一算法；② **token 校验通过后就删除**（原子地检查和删除），同一个 token 不可能被两次下单使用；③ 即使上层有 bug 出现重复，Lua 里的 `hexists` 会把它拦住。

**追问 5：`identifier` 用 UUID 会不会重复？**

**答**：UUID v4 有 122 位随机位，重复概率可以忽略（生日问题下也要生成数十亿亿个才有一半概率碰撞）。**真正需要关注的是"生成方式是否可靠"**——如果用 `Math.random()` 或者时间戳拼随机数，在高并发同毫秒下才会重复。

**追问 6：不依赖 Redis 的方案有吗？🔴（高频刁难）**

**答**：有，但要看清代价。目标是防超卖，本质是"**用某种串行化机制保护库存的读-改-写**"：

| 方案 | 做法 | 代价 |
|---|---|---|
| 数据库原子扣减 | `UPDATE stock SET num = num - 1 WHERE id = ? AND num >= 1`，靠 InnoDB 行锁串行 | **热点行更新**：同一行被大量事务排他锁住，吞吐瓶颈明显，行锁等待会导致连接池打满 |
| 分批/分桶 | 把 1000 库存拆成 10 桶各 100，请求按 userId hash 路由到桶，扣各自的桶 | 无热点，但**可能少卖**（某桶空了别的桶还有），要配"桶间调配"逻辑 |
| 队列串行化 | 请求全部丢进队列，单线程消费扣减 | 吞吐受单消费者限制，延迟高 |
| 悲观锁 | `select ... for update` 锁住库存行 | 同第一条，更重 |

**结论**：不用 Redis 也能防超卖，但都要么牺牲吞吐、要么牺牲"不少卖"。**我选 Redis Lua 的核心原因是"热点行更新"这道坎**——数据库的 `UPDATE` 在几十万 QPS 下是不可能扛住的，我项目的 DB 侧还配合了 Inventory Hint 来缓解（见 Q3.3）。

**追问 7：那什么情况下会"少卖"？怎么解决？🔴**

**答**：少卖 = 库存还有，但用户买不到。典型来源：
1. **Redis 扣成功但后续（建单/MQ）失败** → 现场没释放 Redis 库存 → 需要补偿回滚；
2. **分桶方案下桶间不平衡** → 桶 A 空了但桶 B 还有；
3. **Redis 侧库存与 DB 侧库存对不上**（比如加库存时只改了 DB 没改 Redis）。

解决：① 扣减的每一步失败都要有**回滚路径**（increase 把库存加回去）；② 定期**对账**——比对 Redis 流水与 DB 实际扣减记录，发现差异告警并人工/自动修复。

### Q3.3 数据库侧怎么防超卖？不加锁行不行？🔴

**答**：DB 侧的超卖靠**两条**：
1. **带条件的原子扣减**：`UPDATE ... SET saleable_inventory = saleable_inventory - #{quantity} WHERE ... AND saleable_inventory >= #{quantity}`。返回的**影响行数**是关键——**影响行数为 0 就说明库存不足**，这就是"扣减为负数"的防线。整个语句是原子的，不需要在应用层先查再判断（那才会超卖）。
2. **Inventory Hint**（阿里云 RDS 特性）：`UPDATE /*+ COMMIT_ON_SUCCESS ROLLBACK_ON_FAIL TARGET_AFFECT_ROW 1 */`。它让"更新成功后立即提交、不满足条件就回滚"，并允许一行更新在行锁冲突时**快速失败而不是排队等待**，专治热点行更新。

**追问 1：为什么加 `saleable_inventory >= #{quantity}` 就不会超卖？**

**答**：因为 InnoDB 的 `UPDATE` 会对命中的行加**排他锁**，并在锁内重新读取最新值再判断——`WHERE` 条件和 `SET` 在同一个原子操作里。两个并发事务串行执行：第一个扣完（比如剩 0），第二个 `where` 条件不成立，影响行数为 0，应用看到 0 就返回失败。

**追问 2：`UPDATE` 的行锁锁的是什么？没有索引会怎样？🔴**

**答**：InnoDB 的行锁是**加在索引记录上**的（不是加在"行数据"上）。
- 如果 `WHERE` 命中**唯一索引/主键**，锁的是那一条索引记录（Record Lock）；
- 如果命中**普通索引**，会锁住索引记录 + 对应的主键记录；
- 如果**没有索引**，InnoDB 只能**扫全表并锁住所有扫描到的记录**，等效于锁了全表——这是生产事故级别的问题（并发直接归零）。
所以：**`WHERE` 条件一定要走索引**，这也是为什么扣减 SQL 必须带上主键或唯一键条件。

**追问 3：那这个方案在超高并发下有什么问题？**

**答**：热点行问题——同一行的排他锁让事务排队，**QPS 上不去**，而且锁等待会占用连接、拉长 RT，最终连接池打满雪崩。所以我把 DB 扣减**从下单高峰后移到了支付成功后的低 QPS 阶段**，下单高峰只碰 Redis；DB 侧配合 Hint 在少数需要即时扣减的场景里减少排队。

### Q3.4 为什么要以数据库为准？Redis 和 DB 的库存怎么保持一致？🔴

**答**：**Redis 是用来"挡流量"的，数据库是"账本"**。任何时候两者冲突，以 DB 为准——因为最终的商品归属、订单记录都在 DB，Redis 只是一层可重建的计数缓存（数据丢了可以拿 DB 重建，反过来不行）。

一致性路径：
1. **扣减**：下单同步扣 Redis → 支付成功后扣 DB；两边的扣减请求都带同一个幂等号，保证不会重复扣；
2. **回滚**：关单/取消失败时，Redis 用 `increase`（同样是 Lua 幂等 + 记流水）加回库存，DB 用原子的 `+` 操作加回；
3. **对账**：用 Redis 流水（保留 24 小时）与 DB 记录做比对，发现不一致告警。

**追问 1：那"先扣 Redis 后扣 DB"中间 Redis 挂了/数据没了怎么办？🔴**

**答**：Redis 挂了就**不能卖了**——这是设计上的取舍：库存的唯一可卖掉数就是 Redis，它不可用时无法安全地判定剩余量。降级策略是**接口返回系统繁忙/暂停秒杀**（快速失败），而不是"回退到查 DB 扣 DB"（那样会瞬间把洪峰全压到 DB，就是雪崩）。
恢复后怎么重建：根据 DB 的已售数量 + 未完成订单的预占量，**重新初始化 Redis 库存**。

**追问 2：为什么流水要保留 24 小时而不是永久/立即删？**

**答**：`invalid()` 里库存 key 立即删除，但流水 Hash **延迟 24 小时过期**。原因是**库存缓存失效之后仍要能对账**——如果流水和库存同时没了，之前那批扣减就无从追溯了。24 小时覆盖"当日订单全部关闭或支付"的时间窗。

**追问 3：极端并发下"起始值"会不会重复？（流水设计的追问）**

**答**：流水是一条条独立记录（Hash 的 field 是幂等键），不存在"起始值重复"的问题——`from` 和 `to` 是**每条流水自己的快照**，只用于事后核对"这次从多少变成了多少"。真正可能重复的是**幂等键**，而幂等键来自唯一 token，天然不会重复。

**追问 4：加库存怎么办？秒杀过程中能加吗？🔴**

**答**：项目里 `increase` 走的是与 `decrease` 对称的 Lua（幂等 + 原子加 + 记流水），并支持"冻结/解冻"（`freezeInventory` / `unfreezeInventory` / `unfreezeAndSale`）。
但**秒杀进行中一般不允许加库存**——原因是**本地售罄标记**（见 Q3.5）：一旦售罄，本地缓存已经记了"售罄"，加库存只改 Redis 不改本地缓存，会出现"实际有库存但本地直接拒绝"的不一致。项目里的处理是**加库存时同时 invalidate 售罄标记**，但受本地缓存特性限制，极端情况下有**分钟级不一致**，这是业务上接受的（代码注释里明确写了这个取舍）。

### Q3.5 本地售罄标记是干什么的？一致性怎么保证？🔴

**答**：用 **Caffeine 本地缓存**记"某商品已售罄"。命中这个标记的请求**直接在应用内存里被拒绝，连 Redis 都不去**——目的是把无效流量拦在最外层（用户简历里写的是"拦截 90%+ 的无效秒杀流量"）。

触发与清除（`InventoryFacadeServiceImpl`）：
- **写入**：扣减后剩余为 0（或者扣减失败且原因是"库存已为 0"）→ `soldOutGoodsLocalCache.put(goodsType + SEPARATOR + goodsId, true)`（`:102`）；
- **读取拦截**：`decrease` 和 `queryInventory` 入口处 `getIfPresent(...) != null` 直接返回库存不足/0（`:234`、`:102` 前置）；
- **清除**：`increase` 成功后库存 > 0 时 `invalidate`（`:148`），`invalid` 时也清（`:171`）。

**追问 1：多台机器上的本地缓存怎么保证一致？🔴**

**答**：**保证不了，是刻意接受的弱一致**。多实例各自的 JVM 各有一份标记，A 实例发现售罄、B 实例可能还不知道。
代价与收益的权衡：不一致的后果是"B 实例多放进来几个请求，到了 Redis 层发现没库存后失败"——**最终正确性由 Redis 保证，本地缓存只负责快速失败**。收益是拦掉了绝大多数无效请求。这是典型的"**用可控的不一致换吞吐**"。

**追问 2：那怎么保证 Redis 不会因为本地缓存而少卖？** 🔴

**答**：这是这套设计真正的风险点，工程上靠三件事兜：
1. **售罄标记只在"确实为 0"时写入**，不是"库存不足"（比如要 2 件只剩 1 件不会标记售罄）；
2. **加库存时清除标记**，虽然本地缓存清不干净其他实例，但**其他实例的请求最多也就是多跑一次 Redis**，不会错卖；
3. **短 TTL 兜底** + 对账——如果所有实例的标记都清了（库存回补），最坏情况是等到下一次标记自然过期/刷新。

**追问 3：Caffeine 和 Redis 的定位区别？为什么不直接用 Redis？**

**答**：**Caffeine 是进程内缓存**（JVM 堆内，纳秒级，但每个实例一份、重启即失）；**Redis 是进程外共享缓存**（网络往返、毫秒级，但全局一份）。用 Caffeine 存售罄标记是因为这个判断**极高频率、极低变化、且判断错了也只是多跑一次 Redis**——没必要为它付网络成本。
反过来说，**库存的真实数值必须放 Redis**，因为它需要全局唯一。

**追问 4：JetCache 的多级缓存和这里的 Caffeine 是一回事吗？**

**答**：不是。JetCache 的 `cacheType=BOTH` 是**通用缓存框架**，本地 Caffeine 只是它的一级缓存，有统一的注解和刷新策略，适合业务数据（藏品、用户）。**售罄标记是手写的 Caffeine 用法**（直接 `getIfPresent/put/invalidate`），因为它是一个"专用开关"，不需要 60 分钟刷新那套机制。

### Q3.6 扣完库存后，服务挂了/建单失败/记流水失败怎么办？🔴

**答**：这是"最终一致"的核心问题，分三种情况：

1. **扣减成功、记流水失败**：不可能部分成功——两者在**同一个 Lua 脚本**里，要么都执行要么都没执行。
2. **Redis 扣减成功、MQ 消息没发出去**：用**事务消息 + 回查**保证"本地事务成功 ⇔ 消息投递"；如果本地事务本身执行失败，消息不回滚投递，同时**Redis 库存不会悬空**，因为扣 Redis 和事务消息的回调在同一个本地事务流程里（`InventoryDecreaseTransactionListener`）。
3. **消息投递了、消费失败/超时**：消费端做**幂等 + 重试**；重试仍失败则进入补偿流程——**延迟消息 + 定时任务**把 Redis 库存加回去（`increase`），DB 侧不产生订单。

**追问 1：为什么"扣减流水失败"这个场景不会发生？**

**答**：因为 Lua 脚本内部是顺序执行的同一个请求，`set` 库存和 `hset` 流水之间没有网络边界；如果脚本在语法/类型层面报错，会在**写之前的校验阶段**就失败。

**追问 2：消息重投会不会导致库存重复扣减？🔴**

**答**：不会，靠**幂等键**。消费端处理消息时，用消息携带的**幂等号**（业务唯一标识，如订单号或本次下单的 identifier）作为去重键：
- Redis 侧：Lua 里的 `hexists` 判断流水是否已存在；
- DB 侧：库存流水表/订单表上的**唯一索引**兜底。
重复投递的第二次直接识别为"已处理"，返回成功（幂等语义），不产生副作用。

**追问 3：可靠性上还有别的兜底吗？**

**答**：**定时对账任务**。项目的 `nft-turbo-check` 模块就是干这个的——比对 DB 订单、支付单、库存流水的状态，发现差异记为 mismatch 记录并告警。**"有对账"本身就是一致性设计的最后一道防线**，面试时说这句很加分。

### Q3.7 详情页的防重 token 是什么？什么时候生成、存多久？🔴

**答**：用户进入**商品详情页**时，后端生成一个**一次性 token** 返回；用户点"立即购买"时带回这个 token。服务端做的是"**原子地检查并删除**"——存在则放行（并删掉），不存在则拒绝（重复提交）。

**追问 1：token 存在哪？存多久？**

**答**：存 Redis，有效期在 30 分钟级别（要覆盖用户"打开详情页思考一会儿再下单"的时间）。

**追问 2：为什么需要这个 token？前端按钮置灰不行吗？**

**答**：前端置灰只防"手滑点两下"，防不住：① 用户开两个页面/两个浏览器；② 请求已经发出去了但响应慢，用户刷新重试；③ **脚本/爬虫直接打接口**。服务端的一次性 token 是**唯一可靠**的防重手段。

**追问 3：检查和删除怎么保证原子性？**

**答**：必须原子，否则并发两个请求都"检查通过"就都放行了。实现用 **Lua**（`get` + `del` 一个脚本）或者 Redis 的 `GETDEL`。

**追问 4：一个用户拿一批 token 反复刷怎么办？**

**答**：这是个好问题（真实面试里也被问到了）。防护链条是**多层**的：
1. **token 是一次性的**，每个 token 只能用一次；
2. **库存和限购**兜底——即使刷出多个 token，第 N 次之后库存不足/超过限购数量，业务层面就被拦了；
3. **限流**——网关和接口层对同用户的下单频率做限制；
4. 更严格的场景可以**给 token 绑定商品 + 用户**，并且对同用户同商品的并发下单加**幂等锁**。

**追问 5：详情页访问量很大，token 会不会太多？有什么优化空间？🔴**

**答**：会有问题，优化方向：
- **存储成本**：token 用短 TTL + Redis 定期清理；如果只是防重，其实可以**不预生成 token**，改成"用户 ID + 商品 ID"做幂等键（服务端天然幂等，不需要额外的 token 存储）；
- **访问量**：详情页本身要被缓存（藏品详情走多级缓存），token 生成也能走本地缓存/批量；
- **极端方案**：把防重下移到"业务幂等"——同一用户对同一商品在短时间窗内只允许一次下单，用 Redis 的 `setnx` 一个 `userId+goodsId` 的键实现，省掉 token 这一层。
**但要说清代价**：那样会牺牲"用户确实想买两次"的合法场景（比如限量 2 件），所以 token 方案在"可精确表达一次购买意图"这一点上更准确。

# 第 4 章 · 订单模块（分库分表 / 超时关单 / 防重）

### Q4.1 订单模块做了哪些功能？

**答**：下单建单、订单状态流转、订单查询（买家维度、卖家维度、后台维度）、关单（用户主动取消、超时自动关单、后台/被动关单）、库存回退。

**追问：订单有哪些核心字段？**

**答**：订单号、买家 ID、卖家 ID、商品 ID/名称/图片快照、数量、单价、订单金额、订单状态、支付相关字段、创建时间、过期时间、`lock_version`（乐观锁版本号）、**逆序买家 ID**（分片查询用）。

**追问：字段冗余了买家昵称，买家改名了怎么办？**

**答**：下单时把**展示所需的快照字段**（商品名、商品图、价格）冗余在订单上，这是**有意为之**——快照代表"下单那一刻的事实"，商品后来改价不该影响历史订单。
但**买家的昵称不该冗余成"事实"**，它是"当前值"——改名后历史订单应该显示新名字。项目里的处理是订单只存买家 ID，昵称在**查询时**从用户服务取（有缓存，成本很低）；如果确实要冗余，就必须在改名时**同步刷历史订单**或者**只在展示层做动态替换**。判断标准是：**这个字段是"当时的快照"还是"实体的当前属性"**。

### Q4.2 订单为什么分库分表？怎么分的？🔴

**答**：订单是**增长最快、最大**的表，单表数据量到千万级后索引变高、查询变慢，所以要拆。

**怎么分**：
- **只分表，没分库**（降低部署复杂度，分表跑通了分库只是加配置）；
- **分表数**：`(存量 + 年增量 × 保存年限) / 2000万 → 向上取 2 的幂` → **4 张表**（`order/application.yml:39` `actual-data-nodes: ds.trade_order_000${0..3}`）；
- **分片键：买家 ID**（`mainColum: buyer_id`），因为查询订单绝大多数是"我买的"，用卖家 ID 会造成**数据倾斜**（大卖家一个人占一张表）；
- 用 **ShardingSphere-JDBC** 以 JDBC Driver 方式接入，对 ORM 透明；
- 双分片键 `buyer_id,order_id` + 自定义算法 `TurboKeyShardingAlgorithm`（`:45/64`）。

**追问 1：为什么是 4 张？为什么取 2 的幂？🔴**

**答**：4 张是按数据量算出来的——按每单约 200 字节、单表控制在 2000 万行以内，支撑"约 1 亿订单"量级需要这么多。
取 2 的幂的原因是**路由用哈希取模**（`Math.abs(hashCode) % tableCount`），取 2 的幂之后可以用**位运算**代替取模（`hash & (n-1)`），也方便未来扩表时做"翻倍扩容"（从 4 到 8，每个老表的数据可以均分到两个新表，只需搬迁一半数据）。
**但要说清代价**：非 2 的幂也能取模，只是位运算优化不成立；反过来，如果一开始选 4 张而后数据增长远超预期，扩到 8 张是需要**数据迁移**的——这也是"基因法把表下标编进订单号"的一个隐患（见下一问）。

**追问 2：为什么不直接分库？**

**答**：分库解决的是**单库连接数/IO/容量瓶颈**，分表解决的是**单表数据量瓶颈**。项目的量级下 4 张表还在同一个库能扛住，先分表成本最低（不动部署、不动连接配置）。
分库的分界线是"单库的连接数和磁盘 IO 成瓶颈"，那时候要把分表规则升级成"库 + 表两级路由"，ShardingSphere 支持配置但要改配置和迁移数据。**所以正确说法是"先分表，量到了再分库"，而不是"分表比分库好"。**

**追问 3：为什么用买家 ID 不用订单号做分片键？**

**答**：因为**查询模式**。用户查"我的订单"是按买家 ID 查的，用买家 ID 做分片键能让这类查询**只落一张表**；订单号虽然也能路由，但订单号是"结果"而不是"查询条件"，用户进来的时候还没有订单号。
反过来说，**后台按卖家 ID / 按时间查订单就走不了分片** —— 项目的解法是这类查询走 **ES**（Canal 监听 binlog 同步过去）。

**追问 4：分片键选错了会怎样？**

**答**：两个后果：① **数据倾斜**（某个分片特别大，其他空闲）；② **跨分片查询**（大多数查询要广播到所有分表再归并，性能大幅退化）。所以分片键的选择标准是"**分布均匀 + 高频查询能带这个键**"。

### Q4.3 订单号是怎么设计的？什么时候生成？为什么不预生成？🔴

**答**：结构与生成时机：
- **结构（三段式）**：`业务码(2位) + 雪花序列(19位) + 表下标(4位)`，例如 `10` + `1769649671860822016` + `0002`（`DistributeID.generate`）；
- **业务码**：`BusinessCode` 枚举里定义，`TRADE_ORDER(10, 4)` 表示业务码 10、分 4 张表（`BusinessCode.java:8`）；
- **表下标**：由买家 ID 经分片策略算出（`Math.abs(hashCode) % tableCount`），补零到 4 位；
- **生成时机**：**下单时生成**，不预生成。

**为什么不预生成**：预生成（比如详情页就给用户一个订单号）有隐患——① 用户拿到订单号却不下单，号就浪费了，且**号段里有空洞**看不出异常；② **订单号包含买家 ID 的分片基因**，而买家是谁在"下单那一刻"才确定（详情页可能是未登录状态）；③ 预生成的号存在哪？还要额外维护"预生成池"，复杂度上了却没收益。

**追问 1：雪花算法介绍一下。🔴**

**答**：64 位 long，结构是：
- **1 位符号位**（固定 0，保证正数）；
- **41 位时间戳**（毫秒级，可用约 69 年）；
- **10 位工作机器 ID**（5 位数据中心 + 5 位机器，最多 1024 个节点）；
- **12 位序列号**（同一毫秒内最多 4096 个 ID）。

**特点**：趋势递增（对 B+ 树索引友好，不像 UUID 那样随机导致页分裂）、本地生成不依赖中心服务（性能高）、ID 里隐含时间信息（可反解生成时间）。
**代价**：依赖时钟，时钟回拨会重复。

**追问 2：时钟回拨了解吗？怎么解决？🔴**

**答**：回拨会导致"同一毫秒的序列号被复用"→ **ID 重复**。常见处理：
1. **小幅回拨（几毫秒）→ 等待**：自旋等到时间追上上次的生成时间；
2. **大幅回拨 → 拒绝服务/报警**：宁可失败也不生成可能重复的 ID；
3. **用备用 workerId**：回拨时换一个 workerId 的段落继续发；
4. **记录上次时间戳 + 序列号**：检测到回拨时递增序列号并借位（比如把序列号扩一位），保证唯一。

**Hutool 的 `IdUtil.getSnowflake()`** 在检测到时钟回拨时会**抛异常**（这是保守做法）。生产上更好的方案是像美团 Leaf 那样"小幅回拨等待 + 大幅回拨切换 workerId"。

**追问 3：WorkerId 是怎么设计的？怎么保证每台机器不一样？🔴**

**答**：项目里 `WorkerIdHolder` 在启动时从 **Redis 自增**取值，再 `% 32` 得到 workerId。这样多个实例启动时拿到不同的值。
**代价必须主动说**：① **强依赖 Redis**——Redis 挂了应用起不来（或者拿不到 workerId），项目里的说法是"Redis 挂了应用都无法启动"；② `% 32` 意味着机器数超过 32 就会出现**不同机器拿到同一个 workerId**，进而可能生成重复 ID；③ 如果实例重启，Redis 自增的值会继续往上走，理论上超过 32 后就覆盖了。
更稳的方案是：**用 Nacos/配置中心的实例元数据**（每台机器配一个固定且唯一的 workerId）或者**基于本机 IP/MAC 计算**（有冲突风险），再或者**把机器数控制在 32 以内并做启动校验**。

**追问 4：为什么用雪花算法不用 Redis 自增 ID / UUID？🔴**

**答**：
- **不用 Redis 自增**：自增 ID 可预测（看到 10000 就知道下一个是 10001）→ **水平越权**（用户改 URL 里的 ID 就能遍历别人的订单）+ **暴露真实单量**（商业机密）；
- **不用 UUID**：36 位太长、无序，作为**聚簇索引主键**会导致 B+ 树随机插入、页分裂、写放大，且占空间大；
- 雪花：**唯一 + 趋势递增 + 本地生成 + 不可预测**，四项都占。

**追问 5：为什么要把买家 ID 编进订单号（基因法）？**

**答**：为了解决**"拿到订单号但要查订单时，不知道去哪张表"**的问题。订单号末 4 位就是分片结果，解析出来直接命中单表，**免去广播到 4 张表再归并**。
`DistributeID.valueOf(id)` 按 `substring(0,2)` / `substring(2, len-4)` / `substring(len-4, len)` 反解（`DistributeID.java`）。
**一个细节值得主动说**：解析时是**按"长度 - 4"取的，不依赖雪花序列固定是 19 位**，所以雪花 ID 位数变化不会破坏解析（但会被 `valueOf` 前面的固定 2 位业务码约束）。

**追问 6：那如果以后扩表（4 → 8），订单号里的表下标怎么办？🔴**

**答**：这是基因法的固有代价——**已生成的订单号里的 2 位表下标是按旧规则算的**。扩容时不能简单地"用新规则重算表下标"，否则老订单会被路由到不存在的表。
处理办法：① 保留"老数据用老规则、新数据用新规则"的**双规则路由**（ShardingSphere 自定义算法里可以按订单号长度/生成时间判断）；② 或者做一次**数据迁移**，把老表数据按新规则搬完再切。我倾向在新订单上用新规则（并让订单号里的表下标位数足够表达新表数），旧订单仍按旧规则路由。

### Q4.4 订单状态怎么设计？已支付和已完成有什么区别？🔴

**答**：订单是一条**状态机**，大致是：

```
CREATED(待支付) --支付成功--> PAID(已支付) --藏品铸造/上链完成--> FINISH(已完成)
      |                            |
      |超时/用户取消                |（异常）
      v                            v
  CLOSED(已关闭)                CLOSED/异常态
```

- **已支付 PAID**：钱到账了，但**业务还没交付完成**（藏品还没铸造、还没上链）；
- **已完成 FINISH**：后续所有动作（创建持有藏品记录、上链确权）都完成了，这是一次交易的**终态**。

**追问 1：状态用枚举还是数字？**

**答**：DB 里存**数值/短字符串**（省空间、便于索引），Java 层用**枚举**（`TradeOrderState`）承载"某个状态下允许哪些流转"的逻辑。用状态机而不是散落的 if-else，好处是**状态流转规则收敛在一处**——新增状态时只改状态机，不会漏掉某个分支。

**追问 2：为什么不用 Spring StateMachine？**

**答**：**重**。Spring StateMachine 提供了完整的状态机建模（状态、事件、动作、守卫、持久化），但接入成本高、概念多，而订单状态只有 5~6 个、流转规则清晰、且流转**大部分发生在数据库事务里**（需要和订单表更新一起提交）。用枚举 + 显式流转校验（或简单的状态机工具）就够了。**判断依据是"状态数和流转复杂度"**：超过十几个状态、有多种事件来源（用户/系统/外部回调）时才值得上框架。

**追问 3：状态流转怎么做并发控制？🔴**

**答**：用**乐观锁版本号** `lock_version`。更新时 `UPDATE ... SET state=?, lock_version=lock_version+1 WHERE id=? AND lock_version=?`，影响行数为 0 说明有别人改过，放弃本次更新（重试或返回失败）。
**为什么不加悲观锁**：① 悲观锁（`select for update`）会**长时间持有行锁**，订单状态更新虽然不密集，但在支付回调这种"外部系统触发、可能重试"的场景下很容易出现锁等待；② 乐观锁在冲突少的时候**没有任何锁开销**，而订单状态更新的冲突概率本来就低（同一订单的并发修改是异常情况）。

**追问 4：如果"支付成功"和"超时关单"同时发生怎么办？🔴**

**答**：这是经典的**并发状态推进**问题，两道防线：
1. **乐观锁 / 状态前置判断**：所有状态流转都是"**CAS 式**"的——`WHERE state = 期望的前置状态`。关单的条件是 `state = 待支付`，支付成功的条件是 `state = 待支付`；两者只有一个能成功，另一个影响行数为 0。
2. **业务上的兜底**：如果支付回调发现订单已经被关单了，**不能简单丢弃**——钱已经收了。正确处理是**发起退款**（这正好是项目里"支付成功但订单已关闭"的退款场景，见 Q5.4），并记录一条异常流水供对账。

### Q4.5 重复下单是怎么产生的？怎么解决？🔴

**答**：来源有三类：① 用户**重复点击**（按钮没置灰或网络卡）；② 请求**超时重试**（前端/网关/负载均衡重试）；③ **恶意刷接口**。

解决是一套组合拳：
1. **前端**：按钮置灰 + loading 态（最弱的防线）；
2. **一次性 token**：详情页生成、下单消费并删除（`TOKEN_THREAD_LOCAL` 从请求头取到 token，塞进 `orderCreateRequest.identifier`，`TradeController.java:258/287`）——这是**服务端**的防重点；
3. **幂等键**：把 token 作为整条链路的幂等号，Redis Lua 的流水、DB 唯一索引都用它；
4. **限流**：同用户下单频率限制。

**追问 1：token 是怎么在服务间传递的？🔴**

**答**：项目里是**请求头带 token**，网关或过滤器把它放进 `ThreadLocal`（`TokenFilter.TOKEN_THREAD_LOCAL`），业务代码从 ThreadLocal 取出塞进下单请求参数。
**这里的坑**：ThreadLocal 在**异步/线程池**场景下会丢（子线程拿不到父线程的值），必须用 `InheritableThreadLocal` 或 **TTL（TransmittableThreadLocal）**。项目里引入了 TTL 解决线程池传递问题。

**追问 2：不同商品会不会互相干扰？**

**答**：不会，因为 token 是**按"一次下单意图"**发的，且 Redis 流水键里带了商品维度（`getCacheStreamKey(request)` 由商品类型 + 商品 ID 组成）。同一个 token 拿去下另一个商品，会在设计上被识别为不同的 identifier 或者直接被拦。

### Q4.6 超时关单怎么做？为什么不用延迟消息？🔴🔴

**答**：关单有三种触发：**用户主动取消**、**超时自动关单**、**后台/被动关单**（风控、运营）。

超时关单用 **XXL-JOB 定时扫表**：
1. **XXL-JOB 分片广播**：多实例按 `shardIndex/shardTotal` 分摊，项目里按**买家 ID 尾号**分片，多个执行器并行扫不同的尾号区间，互不重复；
2. **单机内并发**：每个执行器内部用"**生产者-消费者 + 线程池**"（ForkJoinPool）+ **毒丸对象**标记结束，把扫出来的订单一并发出去处理；
3. **处理动作**：推进订单状态为已关闭 + 用事务消息保证"关单 + 库存回退"一致。

**为什么不用 MQ 延迟消息**（这是面试题里问得最狠的一条，四个理由都要说）：
1. **海量消息积压成本高**：每个订单都要发一条延迟消息，千万级订单就是千万级消息堆在 Broker 里；
2. **MQ 无法保证 100% 不丢**：延迟消息一旦丢失，这个订单就永远关不掉了——**少关了单就锁着库存**，代价比"多扫一次表"大得多；
3. **大量无效消息**：绝大多数订单会**提前支付或主动取消**，那条延迟消息到达时已经没用了，纯粹浪费；
4. **扩展性差**：延迟级别（RocketMQ 固定 18 个延迟档位）不灵活，业务要改过期时间就得改消息级别；而且消息堆积时无法按业务优先级处理。

**追问 1：那扫表方案怎么保证不漏？**

**答**：**扫表天然可重入、可重跑**——定时任务不管扫几次，只要状态条件和时间条件是幂等的（`WHERE state = 待支付 AND 创建时间 < 现在 - 30分钟`），重复扫描的结果就是重复处理同一批数据，而处理动作本身是幂等的（状态 CAS）。**这是"查询驱动"相对"消息驱动"的核心优势：状态在数据库里是持久的事实，不需要额外的消息来触发。**

**追问 2：那个扫表 SQL 能走索引吗？哪个索引？🔴**

**答**：原 SQL 大致是 `select id from trade_order where order_state = 2 and gmt_create > #{expireTime} and reverse_buyer_id like '%xx' and id > #{lastMaxId} limit 200`。
- **`like '%xx'`（likeLeft）走不了索引**——对列做前置通配等于无法用最左前缀，只能全表扫；
- **优化**：新增**逆序冗余字段 `reverse_buyer_id`**（把买家 ID 反过来存），把条件改成 `reverse_buyer_id like 'xx%'`（likeRight），命中索引；
- 并建 **联合索引 `(reverse_buyer_id, order_state, gmt_create)`**，让"分片条件 + 状态 + 时间"三者在索引里连续；
- **`id > #{lastMaxId}` 是游标分页**（keyset pagination），避免 `limit offset` 深分页——深分页要扫描并丢弃前 N 条，越翻越慢；用"上一批最大 ID"作为游标，每批都是索引定位 + 取 200 条。

**追问 3：为什么用 `order_state = 2` 这种状态过滤，`state` 有几种、索引有效果吗？**

**答**：状态值很少（5~6 种），**单看状态列选择性很差**（可能 90% 的订单都是"已完成"），单独用它做索引效果不好。所以必须**组合索引**，并且让**选择性高的列排在前面**——这里 `reverse_buyer_id`（分片条件）和 `order_state`（筛掉已完成的）组合起来就能把范围缩到很小。

**追问 4：多久扫一次比较合适？一分钟处理不完怎么办？🔴**

**答**：扫表频率要平衡"关单的及时性"和"任务对系统的压力"。项目里是**分钟级**（订单过期时间是 30 分钟量级，所以关单延迟几分钟完全可接受）。
处理不完时的应对：
1. **加并行度**——分片数（`shardTotal`）随实例数增长，XXL-JOB 的分片广播天然支持水平扩容；
2. **限流 + 分批**——每批 200 条，处理完再取下一批，避免一次性把内存打爆；
3. **错峰**——把扫表任务和业务高峰期错开；
4. **兜底**：如果持续堆积，说明过期订单量已经超过系统处理能力，要么**提高扫描频率**，要么**改用"订单创建时写一条延迟任务记录"**（自研延迟表 + 定时扫，比 MQ 可控），或者**下游放弃"关单即回滚"改为"先批量关单、再批量回滚库存"**两步走。

**追问 5：这个 SQL 的执行顺序你清楚吗？（`select ... from ... where ... limit`）**

**答**：逻辑执行顺序是 `FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT`。注意 **`SELECT` 在 `ORDER BY` 之前**（这也是 MySQL 允许 `ORDER BY` 用 `SELECT` 里别名/列号的原因），而 `LIMIT` 最后执行——所以 `limit offset, size` 的深分页会先把前面所有行都算出来再丢弃。

### Q4.7 订单相关的索引优化：`like %xxx` 为什么不走索引？

**答**：B+ 树索引是**按列值的最左前缀有序**的。`like 'xx%'` 能确定一个起始位置，从那里往后顺序扫描（范围查询）；而 `like '%xx'` 的匹配串在开头是**未知的**，无法确定从哪里开始扫，只能全表扫描（或退化为全索引扫描）。

**追问 1：怎么知道有没有走索引？🔴**

**答**：`EXPLAIN`。看几个关键列：
- **`type`**：`ALL`（全表）、`index`（全索引扫描）、`range`（范围，这个是好的）、`ref`（等值，好）、`const`（常量，最好）；
- **`key`**：实际用了哪个索引；`possible_keys` 是候选；
- **`key_len`**：用到了索引的多少字节（能判断联合索引用了几列）；
- **`rows`**：预估扫描行数；
- **`Extra`**：`Using index`（**索引覆盖**，不用回表，好）、`Using filesort`（需要排序，差）、`Using temporary`（用了临时表，差）、`Using where`（有条件下推到引擎后再过滤）。

**追问 2：怎么让一个 SQL 避免回表？**

**答**：**索引覆盖**——让索引里包含 `SELECT`、`WHERE`、`ORDER BY` 用到的所有列，这样引擎在二级索引上就能拿到全部数据，不用再回主键索引取行数据（`Extra: Using index`）。
**代价**：索引列越多，索引本身越大、写入维护成本越高。所以**只对高频、且列数少的查询做覆盖索引**。

**追问 3：唯一索引和主键索引有什么区别？🔴**

**答**：
| | 主键索引 | 唯一索引 |
|---|---|---|
| 数量 | 一张表只有一个 | 可以有多个 |
| 是否可空 | NOT NULL | 允许 NULL（且多个 NULL 不冲突） |
| 存储 | 聚簇索引，**叶子节点就是整行数据** | 二级索引，叶子节点存主键值，查非索引列要**回表** |
| 用途 | 行的物理组织方式（InnoDB 中表按主键聚簇） | 业务唯一约束（如订单号、手机号） |

**关键点**：InnoDB 里**数据是按主键聚簇组织的**，所以主键建议用**趋势递增**的值（雪花/自增）而不是 UUID——UUID 会让插入位置随机，造成页分裂和写放大。

# 第 5 章 · 支付模块（微信支付 / Seata / 退款）

### Q5.1 支付单是怎么设计的？为什么一个订单会有多个支付单？🔴

**答**：
- **支付单表不绑定订单表**，用**付款方 / 收款方 / 业务单号（bizNo）**做抽象 —— 这样它不仅能服务订单，还能服务其他需要支付的业务（会员、充值），是"领域内聚"的设计；
- 支付单字段：支付单号、业务单号、付款方、收款方、金额、状态、支付方式、支付链接、第三方流水号、创建时间、支付成功时间等。

**为什么一个订单会有多个支付单**：① 用户**换支付方式重试**（先用微信没付成，改用另一个渠道）；② 上一个支付单**已过期**，重新生成一个；③ **多渠道并发支付**（用户开了两个页面）。

**追问 1：那怎么保证"同一个订单在同一个支付方式下只有一个支付单"？🔴**

**答**：**一锁二判三更新**：
1. **加锁**：锁的 key 是 `订单号 + 支付方式`——`@DistributeLock(scene="GENERATE_PAY_URL")`，Redisson 分布式锁；
2. **判重**：加锁后查"该订单 + 该支付方式是否已有未失效的支付单"，有则直接返回**已存在的支付链接**（而不是新建）；
3. **更新/新建**：没有才新建支付单并调第三方生成链接。

**锁的粒度为什么是"订单号 + 支付方式"而不是订单号**：锁订单号会让用户"换渠道"被自己的旧请求阻塞；锁"订单 + 渠道"既能防同渠道重复，又不影响换渠道。

**追问 2：为什么用 Redisson 而不是简单的 setnx？**

**答**：① 需要**可重入**（同一线程可能嵌套调用）；② 需要**看门狗续期**（第三方调用可能超过锁的租期）；③ 需要**安全释放**（比较持有者再删）。Redisson 这些都封装好了，setnx 要自己写 Lua 比较删除 + 自己实现续期。

**追问 3：这里不加锁行不行？**

**答**：可以用**数据库唯一索引**（`订单号 + 支付方式` 唯一）替代——并发时一个成功一个抛唯一键冲突，捕获后返回已存在的支付单。这是**更简单、更可靠**的做法（DB 是最终权威），代价是"靠异常做控制流"、且**并发调第三方支付接口**两次可能产生两个第三方订单（所以还是需要锁或状态标记来防止重复调第三方）。

### Q5.2 微信支付怎么接入的？🔴

**答**：
- **接口版本**：微信支付 **APIv3**；**接入方式**：**Native**（扫码支付，返回一个 `code_url`，前端把它转成二维码）；
- **需要准备**：商户号、APIv3 密钥、**商户 API 证书**（`apiclient_cert.pem` / `apiclient_key.pem`）、平台证书（用于验签回调）；
- **核心接口**：下单（生成支付链接）、支付结果通知（回调）、查询订单、关闭订单、申请退款。

**追问 1：证书起什么作用？🔴**

**答**：两个方向都用到：
- **请求方向**：商户用自己的**私钥签名**请求，微信侧用商户证书验证请求来自合法商户；
- **回调方向**：微信用它自己的**平台证书签名**通知，商户需要下载平台证书并**验签**，确认"这个回调真的是微信发的"，防止伪造回调。
APIv3 用 **RSA + SHA256** 做签名，敏感字段（如用户手机号、退款原因）用**平台证书公钥加密**、商户用私钥解密。
**证书就是个身份凭证**：没有它，你没法证明请求是自己发的，也没法确认回调是真的。

**追问 2：链接怎么变成二维码？**

**答**：Native 下单返回的是 `code_url`（形如 `weixin://wxpay/bizpayurl?pr=xxx`），前端用二维码库（JS 侧 qrcode）把它渲染成图片，用户微信扫一下就能拉起支付。

**追问 3：微信怎么知道回调到哪个接口？**

**答**：下单时**在请求参数里指定 `notify_url`**（回调地址，必须是 HTTPS 且外网可达）。微信支付成功后 POST 到这个地址。
**工程要点**：`notify_url` 要能区分环境（测试/生产的域名不同）、要**公网可达**（本地开发要内网穿透）、**必须做验签**（不能只信报文内容）。

**追问 4：回调丢了怎么办？怎么发现？🔴**

**答**：回调是"**最多通知若干次**"的机制（微信会在一段时间内重试），但不能假设一定到。所以必须有**主动兜底**：
1. **主动查询**：定时任务扫"支付中"状态的支付单，调微信的**订单查询接口**确认实际状态；
2. **对账**：下载**微信账单**，与本地支付单逐笔比对，差异记入 `PayCheckMismatchDetail`。项目里就是这么做的（`PayBillPullJob` / `PayDetailCheckJob` / `PayOrderCheckJob`）；
3. **实时性优化**：对账是 T+1 的，太慢。更实时的做法是**用户端轮询/主动触发查询**——前端支付完成后轮询订单状态，服务端在这条链路里"顺带"主动查一次微信，把结果落库。这就是"用前端轮询做兜底查询"的思路。

**追问 5：回调重投/并发两个回调怎么处理？🔴🔴**

**答**：**幂等**，三层：
1. **Redis 分布式锁** ✅/或 DB 状态 CAS：**这里有争议，要说清** —— 项目里支付回调**没有加分布式锁**，理由见下；
2. **状态判断**：回调进来第一件事 `if (payOrder.isPaid()) return true;`——已支付直接返回成功（幂等语义，避免微信一直重试）；
3. **乐观锁 CAS**：推进状态时带 `lock_version` 条件，影响行数为 0 说明已被处理过。

**为什么支付回调不加分布式锁**：① 加锁会引入 Redis 依赖和网络往返，而**真正的并发点在库存**（已用 DB 原子 SQL + 行锁解决）；② 如果按"藏品"加锁，会让大量正常付费用户抢锁失败；③ 幂等用**状态判断 + CAS** 已经足够——重复回调第二次进来看到状态已是"已支付"就直接返回，不需要互斥。

**追问 6：两个渠道同时支付成功了怎么办？🔴**

**答**：两台渠道分别回调、都成功 → 出现了**多付**。处理：
1. **第一笔回调**正常推进订单到已支付；
2. **第二笔回调**进来时发现"订单已支付，但**本次回调的支付单不是订单当前关联的那一笔**"→ 判定为重复支付；
3. 触发**自动退款**：`doChargeBack(...)`，内部用 **JDK21 虚拟线程** `Thread.ofVirtual()` 异步发起退款（不阻塞回调响应），失败由 `RefundOrderRetryJob` 重试。

**追问 7：为什么退款要用虚拟线程？**

**答**：退款是**IO 密集的外呼**（调微信接口，几百毫秒），如果用平台线程，大量退款会占满线程池；虚拟线程在 IO 阻塞时**自动让出载体线程**，能以极小成本开大量并发任务。**注意**：虚拟线程适合 IO 密集，**CPU 密集任务用它会适得其反**（还有 `synchronized` 阻塞、`ThreadLocal` 开销等问题）。

### Q5.3 支付成功后做了哪些事？一致性怎么保证？🔴🔴

**答**：支付成功回调触发 `paySuccess`，做四件事：
1. **推进支付单状态**（已支付 + 记录第三方流水号）；
2. **推进订单状态**（待支付 → 已支付）；
3. **扣 DB 库存 + 创建持有藏品**（`held_collection`，状态铸造中）；
4. **调链服务上链**（铸造 / 转让）。

**一致性方案**：前面 5 步（订单、支付、库存、藏品）放**Seata AT 全局事务**（`PayApplicationService.java:147` `@GlobalTransactional`）；**第 6 步上链不进事务**，改用 **Seata 事务钩子**：注册一个 `TransactionHook`，在**全局事务提交后**回调执行上链；上链失败由 `ChainProcessJob` 定时重试（`PayApplicationService.java:185`）。

**为什么上链不进事务**（这是本项目的核心设计决策，必须讲透）：
1. **上链是不可靠的外部调用**——文昌链可能超时、可能返回失败，把它放进事务里会**长时间持锁**，甚至因为外部超时导致整个支付事务回滚；
2. 更重要：**"钱已经收了"这件事不能被回滚**——如果因为上链失败把支付事务回滚了，就出现"用户付了钱但订单状态回退了"的灾难；
3. 上链本身是**可重试、最终一致**的（链上操作有独立状态机 `ChainOperateStateEnum`），适合用"本地事务 + 重试"的模式。

**追问 1：为什么要用 Seata AT？它是不是太重了？🔴**

**答**：**"重"是相对的，要看被替代的方案**。支付成功这条链路参与者多（支付、订单、库存、藏品）且跨服务，用 MQ 做最终一致也是可以的，但：
- **AT 对业务侵入最小**：只需要在入口加 `@GlobalTransactional`，各服务不用写补偿逻辑（对比 TCC 要每个参与者实现 try/confirm/cancel，Saga 要编排补偿）；
- **业务要求"支付成功立即可见"**——用 MQ 最终一致，用户付款后要等一段时间才看到订单变化，体验差；
- 冲突也不大：支付回调是**低频**（相对秒杀），AT 的性能开销可以接受。

**追问 2：AT 模式的原理？TM / RM / TC 是什么？🔴**

**答**：
- **TC（Transaction Coordinator）**：事务协调者，**独立的 seata-server**，负责维护全局事务和分支事务的状态、驱动全局提交/回滚、**维护全局锁**；
- **TM（Transaction Manager）**：事务管理器，就是**发起全局事务的那一方**（加了 `@GlobalTransactional` 的方法），负责开启全局事务、最终发起提交或回滚；
- **RM（Resource Manager）**：资源管理器，**每个参与方**（每个被调用服务）都是 RM，负责执行自己的本地事务、注册分支事务、上报状态。

**执行流程**：
- **一阶段**：TM 开启全局事务（生成 XID）→ 调各参与者 → 每个 RM 拦截业务 SQL，**解析 SQL 语义找到要改的数据，保存前后镜像（before image / after image）到 `undo_log` 表**，执行业务 SQL，**然后直接提交本地事务**（业务数据和 undo_log 在同一个本地事务里，保证原子）→ 向 TC 注册分支事务并**申请全局锁**；
- **二阶段（全局提交）**：TC 通知各 RM 提交 → RM **异步删除 undo_log**（很快，因为业务数据已经提交了）；
- **二阶段（全局回滚）**：TC 通知各 RM 回滚 → RM **根据 undo_log 的 before image 做反向补偿**（生成反向 SQL 执行），再删除 undo_log。

**关键点（面试官爱追）**：AT 的**一阶段就提交了本地事务**（不是像 XA 那样两阶段持有锁），所以它**性能好但没有真正的隔离性**——这就是"写隔离靠全局锁、读隔离靠默认读未提交"的来源。

**追问 3：事务都提交了怎么回滚？🔴**

**答**：靠 **undo_log 里的前后镜像**。回滚时 RM 解析 `undo_log`，用 **before image** 生成反向的 UPDATE（把数据改回去），为了只改回"本次事务改动的部分"，它会用 **after image 做条件**。
所以回滚不是"撤销提交"，而是**"生成一条补偿 SQL 把数据改回原样"**——本质是**补偿**，不是数据库级别的回滚。

**追问 4：回滚前有人改了数据怎么办？🔴**

**答**：这是 AT 的**脏写问题**，Seata 的处理是**校验 after image**：
- 回滚前，RM 用 `undo_log` 里的 **after image** 去和当前数据库的值比对；
- **一致** → 说明没人改过，正常用 before image 回滚；
- **不一致** → 说明有**本例事务之外的修改**，此时 Seata **无法安全回滚**，会**抛出异常 / 记录告警**，需要人工介入。

工程上的防线是**全局锁**（下一问）：它本来就是为了"尽量不让外部事务改到同一行"，把脏写概率压到极低。

**追问 5：什么是全局锁？它解决什么问题？🔴**

**答**：全局锁是 **TC 侧维护**的锁（不是数据库锁）。RM 在一阶段执行完本地事务后、提交全局事务前，需要持有"被自己修改的数据行"的全局锁。
作用：**防止"全局事务 A 改过的行，被另一个全局事务 B 在 A 提交前改掉"** —— 也就是**写隔离**。
它可以避免的问题：如果不加全局锁，A 改了库存还没全局提交，B 也改库存并提交了，A 回滚时就会把 B 的修改一起冲掉。
**代价**：全局锁会**串行化**对同一行的跨服务修改，影响并发；而且是跨网络调用 TC 的（有 RPC 开销）。

**追问 6：`select for update` 和普通 `select` 查出来的结果有区别吗？🔴**

**答**：有，本质是**当前读 vs 快照读**：
- **普通 `SELECT`**（RR 隔离级别下）：**快照读**，读的是**事务开始时的一致性视图**（MVCC，通过 undo log 版本链构造），不加锁。所以**看不到别的事务刚提交的修改**（只要那个提交晚于本事务的快照建立时间）。
- **`SELECT ... FOR UPDATE`**：**当前读**，读**最新的已提交数据**并加**排他锁**（锁索引记录）。同类的还有 `LOCK IN SHARE MODE`（共享锁）、以及 UPDATE/DELETE 的读（本身也是当前读）。

**为什么这对 AT 模式重要**：AT 默认的隔离级别是**读未提交**（因为本地事务一阶段就提交了，别人能读到），而如果你在业务里用 `select` 去判断"库存够不够"，**可能读到快照旧值**，所以要读最新值就必须用 `select ... for update`（同时也能借用全局锁/行锁避免并发问题）。

**追问 7：想要开启 AT 事务要做什么？**

**答**：① 引入 Seata 依赖；② 配置 TC 地址（`seata.server` 或注册中心）；③ **给每个 RM 的数据源包上代理**（Seata 的 `DataSourceProxy`，通过 starter 自动配置，这是"拦截 SQL"的入口）；④ 在**发起方**方法上加 `@GlobalTransactional`。
**注意点**：`@GlobalTransactional` 和 `@Transactional` 的**传播行为**要清楚——全局事务开启后，参与方的本地事务被 Seata 的代理接管，才有 undo_log。

**追问 8：为什么不用 TCC？一致性要求高，用 TCC 不是更好吗？🔴**

**答**：TCC 的**一致性强于 AT**（不需要全局锁回滚脏数据、一阶段就预留资源），但代价是**每个参与者都要写 try / confirm / cancel 三个方法**，还要处理**空回滚、幂等、悬挂**三种异常——工作量是 AT 的好几倍。
我这里的判断是：**支付链路虽然重要，但没有到"必须牺牲开发效率换极致一致"的程度**——因为① 参与者之间的修改很少有热点冲突（不像秒杀），全局锁的性能损失可接受；② 有对账兜底。**如果场景是"资金调拨、跨行转账"，我会选 TCC。**

### Q5.4 退款怎么实现的？失败了怎么办？🔴

**答**：**退款单 + 状态机**：
1. 触发场景有两类：**多渠道重复支付**（多付了要退）、**支付成功但订单已被关闭**（超时关单和支付并发导致）；
2. 创建**退款单**（`refund_order`），调微信的退款接口；
3. 退款结果异步返回（微信会有退款通知），也可主动查询；
4. **失败/超时**：定时任务 `RefundOrderRetryJob` 重试。

**追问 1：创建退款单成功、但调退款接口失败怎么办？🔴**

**答**：关键点是**退款单先落库、再调接口**——这样"要退款"这件事有**持久记录**，接口失败只是"还没退成功"的状态，可以被定时任务扫出来重试。
如果反过来先调接口后落库，接口成功后落库失败（或宕机），就会出现"**退了钱但系统不知道**"的黑洞。**"先记录意图，再执行动作，靠重试收敛"**是这类外部调用的通用模式（和上链的处理思路一致）。

**追问 2：退款会不会重复退？**

**答**：靠**退款单的唯一性 + 第三方幂等**。① 同一笔支付单只允许有一个"有效退款单"（唯一索引约束）；② 微信侧的退款接口用**商户退款单号**做幂等，重复请求返回同一笔退款结果。两道都做，才安全。

### Q5.5 如果接入一个新的支付方式，需要改哪些东西？🔴

**答**：理想情况下**只加一个策略实现类**——项目的支付入口用**工厂 + 策略**：
1. 定义支付策略接口（下单、查询、退款、回调解析）；
2. 新增 `XXXPayServiceImpl implements PayService`，实现该渠道的四个动作；
3. 在工厂里按"支付方式枚举"注册映射；
4. 支付单表加/复用"支付方式"字段区分；
5. 配置新的回调地址 + 证书/密钥；
6. **不用改**订单、库存、藏品那些下游逻辑——因为下游只关心"支付成功"这个事件，不关心钱从哪来。

**追问：那实际上还需要动什么？**

**答**：说实话，现实里还要动：① **回调接口**（每个渠道的通知格式/验签方式不同，需要独立的 Controller 和验签逻辑）；② **对账任务**（每个渠道的账单格式不同）；③ **前端**（多一个支付选项、多一个跳转/二维码流程）；④ **配置与路由**（回调地址要在网关放行，不能做登录校验）。**"只加一个类"是理想，能说出这四点才显得真做过。**

### Q5.6 支付模块的难点和亮点是什么？线上出现过什么问题？

**答**：难点两个：
1. **外部系统不可信**：微信回调可能丢、可能重、可能乱序，所以整套设计围绕"**幂等 + 主动查询 + 对账**"展开；
2. **状态推进的并发**：支付回调、超时关单、用户取消三条路径都会改订单状态，必须用 CAS 保证只有一条生效，并且要处理"支付成功但订单已关"这种冲突（发起退款）。

亮点是：
- **支付单与订单解耦**（bizNo 抽象）让支付域可以服务多个业务；
- **一致性按场景分层**——该强的地方（订单/库存/藏品）用 AT，不该强的地方（上链）用钩子 + 重试；
- **重复支付自动退款 + 虚拟线程承载异步退款**。

线上真实问题见 Q1.4（事务消息配置被覆盖、RocketMQ 路由、Date 序列化）。

# 第 6 章 · 一致性与 MQ

### Q6.1 项目里的一致性方案为什么要分那么多种？一条链路不统一吗？🔴

**答**：因为**不同环节的失败代价不一样**，统一方案会把成本浪费在不需要的地方。四种方案按场景：

| 场景 | 方案 | 为什么是它 |
|---|---|---|
| 下单（Redis 扣 + MQ 建单） | **对账 + 补偿**（AP 优先） | 秒杀要的是吞吐，强一致会拖死接口；库存最终以 DB 为准 + 定时对账 |
| 关单（关闭 + 回退库存） | **RocketMQ 事务消息** | 只涉及两方、并发不高；要保证"关单成功 ⇔ 回退消息发出" |
| 支付成功（订/付/藏多方） | **Seata AT** | 参与者多、不适合 MQ，AT 侵入最低，且要求"支付成功立即可见" |
| 上链（外部不可靠调用） | **事务钩子 + 定时重试** | 外部调用绝不能进事务；上链可重试，只需最终一致 |

**一致性时长排序**：AT（最短）> 事务消息 > 定时任务重试 > 对账 + 人工（最长）。**选择的原则是"这个环节错了会造成什么后果"**：多扣库存 → 资损 → 必须强；上链慢 → 体验问题 → 可最终一致。

**追问：这么多方案怎么保证不互相干扰？**

**答**：靠**边界清晰**——每个环节只选一种方案，不嵌套。比如支付成功用的 AT 事务里，**不含**上链（上链在钩子里）；关单用事务消息，**不再套 AT**。混用最大的风险是"事务边界重叠导致锁等待甚至死锁"，也会让排查变得极难。

---

### Q6.2 RocketMQ 事务消息的原理讲一下。🔴🔴

**答**：核心是"**两阶段提交 + 回查**"：

1. **发送半消息（half message）**：Producer 先把消息发到 Broker，但这条消息**对 Consumer 不可见**（存在 `RMQ_SYS_TRANS_HALF_TOPIC`）；
2. **执行本地事务**：Broker 返回发送成功后，Producer 执行本地事务（比如"落库存扣减流水"）；
3. **提交或回滚**：本地事务成功 → 发 **Commit**，Broker 把消息从 half topic 挪到真实 topic，**Consumer 才能消费到**；本地事务失败 → 发 **Rollback**，Broker 删除半消息；
4. **事务回查（关键）**：如果第 3 步因为**网络抖动/Producer 宕机**没有送达，Broker 会**定时回查**（默认从 1 分钟起，逐次加大间隔）——调用 Producer 的 `checkLocalTransaction` 方法询问"刚才那笔本地事务到底成没成"，Producer 根据**本地事务状态表/业务数据**回答，Broker 再决定提交还是回滚。

**追问 1：执行本地事务和回查，是在同步链路还是异步链路？🔴**

**答**：**本地事务执行在发送消息的同步链路里**（`sendMessageInTransaction` 会同步触发 `executeLocalTransaction`，Producer 拿到返回的 `LocalTransactionState` 后才决定提交/回滚），但**回查是 Broker 发起的异步调用**，由 Broker 的定时线程触发，走 Producer 的回查接口。所以"消息一定发出去了"这个事实，是**同步**确认的。

**追问 2：怎么实现一个事务消息？要写什么？**

**答**：① 实现 `TransactionListener` 接口，重写两个方法：`executeLocalTransaction`（执行本地事务，返回 COMMIT/ROLLBACK/UNKNOWN）和 `checkLocalTransaction`（回查时根据本地事务状态回答）；② 生产者用 `TransactionMQProducer` 并注册这个 listener；③ 配置文件里声明 `producerType: Trans` + `transactionListener: xxxListener`（**这就是你踩过的那个坑**——配置被主应用覆盖后，消息退化成普通消息，listener 永远不触发）。

**追问 3：用了事务消息就能保证一定发出去吗？什么情况会失败？🔴**

**答**：**不能保证 100%**。会失败的场景：
1. **Broker 侧持久化失败**（磁盘满、写失败）→ 半消息没存下来；
2. **回查也失败**（Producer 长时间宕机、回查接口异常）→ Broker 无法判定，超时后**默认回滚**（可配置），消息就丢了；
3. **本地事务状态无法判定**（`UNKNOWN` 一直无法决断）；
4. **Consumer 消费失败且重试次数耗尽** → 进死信队列。

所以**"有事务消息"不等于"一致了就完事"**，仍要有**对账**做最后防线。这也是我在项目里保留 `nft-turbo-check` 对账模块的原因。

**追问 4：那如果 MQ 不支持事务消息，你有其他方案吗？🔴（上难度）**

**答**：有四种主流替代方案：

| 方案 | 做法 | 代价 |
|---|---|---|
| **本地消息表** | 本地事务里同时写"业务数据 + 待发送消息"到同一个库，然后定时任务扫这张表发送，发送成功后标记 | 需要额外一张表和扫描任务；发送和标记之间仍有失败窗口（靠重试收敛） |
| **最大努力通知** | 业务先提交，然后尽力发消息 + 定时重试；接收方查证 | 可靠性最低，依赖接收方的主动查询 |
| **RocketMQ 延迟消息 + 定时对账** | 不追求"发消息与事务原子"，改由定时任务补齐 | 一致性延迟 |
| **变更捕获（binlog → MQ）** | Canal 监听 binlog 发消息 | 依赖 Canal 可用性；消息和业务提交天然一致（binlog 只有提交后才有） |

**我项目里其实两种都用到了**：交易链路用事务消息；而 **Canal 监听 binlog 同步 ES** 就是"变更捕获"的思路（严格说它是数据同步，不是事务消息，但原理上解决了"提交即发现"的问题）。

**追问 5：消息是从哪个模块发到哪个模块的？订单模块收到后干什么？**

**答**：下单场景：`trade`（编排）**发送**新购消息（`newBuy-out-0` → `new-buy-topic`），**订单模块**（或消费端）收到后调**库存模块**扣 DB 库存、**创建订单**记录。关单场景：`order` 发 `orderClose-out-0`（`order-close-topic`），消费端执行关单和库存回退。

**追问 6：为什么不用 Kafka？🔴**

**答**：
1. **事务消息**：Kafka 0.11+ 有事务（Exactly-Once），但它的语义是"**流处理事务**"（消费-处理-生产），**不支持 RocketMQ 那种"半消息 + 回查"的业务事务消息**——业务上没法用"发消息和本地事务绑定"这个能力；
2. **延迟消息**：Kafka **原生不支持**（要靠外部轮询/时间轮实现），RocketMQ 支持固定延迟级别（虽然也有限）；
3. **消息回查/重试/死信**：RocketMQ 对"消费失败重试 + 死信队列 + 消息轨迹"的工程化支持更贴合业务系统；
4. **RocketMQ 是阿里系出品**，和项目技术栈（阿里云、Spring Cloud Alibaba）一致，社区资料多。

**Kafka 的优势在别处**：超高吞吐（百万级/秒）、生态（Kafka Streams、Connector）、日志场景的事实标准。**选型是场景匹配，不是谁更强**。

---

### Q6.3 消息不丢、不重、有序，分别怎么做？🔴

**答**：

**不丢（三段都要防）**：
1. **生产端**：用**同步发送 + 重试**；事务消息保"本地事务 ⇔ 消息投递"；失败落**本地消息表**兜底；
2. **Broker 端**：**刷盘策略**用同步刷盘（`SYNC_FLUSH`）+ **主从同步复制**（`SYNC_MASTER`）；
3. **消费端**：**手动 ACK**，业务处理成功才提交 offset（Spring Cloud Stream 里是 `ackMode: MANUAL`）；失败重试，超次数进**死信队列**。

**不重（幂等）**：
- **消费端幂等**：用消息里的**业务唯一键**（订单号 / identifier）做去重——Redis `setnx`、DB 唯一索引、或状态机"已处理则跳过"。**这是必须做的**，因为"至少一次投递"是 MQ 的默认语义。

**有序**：
- **同一队列 + 同一 key**：RocketMQ 用**顺序消息**（`MessageQueueSelector` 按业务 key 选队列，保证同一订单的消息进同一队列，队列内单线程消费）；
- 或者**不用顺序，用状态机兜底**——大部分业务不需要严格顺序，只要有"状态校验 + 幂等"，乱序到达也能被正确处理（这是更常用的做法）。

**追问：我们项目的消息需要有序吗？**

**答**：**不需要严格有序**。因为消息处理是**幂等**的，而且业务状态推进有前置校验（比如"关单"要求订单处于待支付）。乱序到达时，后到的消息会因为状态不符而被幂等地跳过或拒绝。**要顺序的时候再要顺序，不然会白白牺牲并发度。**

---

### Q6.4 消费端的幂等是怎么设计的？幂等号从哪来？🔴

**答**：同一条链路上的幂等号是**贯穿的**：
- 下单：**详情页的一次性 token** → 作为 `identifier`，一路带到 Redis 流水键（`DECREASE_<identifier>`）、消息体、订单表唯一索引；
- 支付：**支付单号 / 第三方支付流水号**；
- 关单：**订单号**。

处理方式按层：
1. **Redis 层**：Lua 里的 `hexists` 判断流水是否已存在（`OPERATION_ALREADY_EXECUTED` 视为成功）；
2. **DB 层**：唯一索引（订单号、支付单号）+ 状态 CAS；
3. **消息层**：消费前先查"这笔业务是否已处理"（幂等表或业务状态表）。

**追问 1：幂等键用什么生成？UUID 会不会重复？**

**答**：用 UUID/雪花都可以，重复概率可忽略。**重点是"幂等键的生命周期要和业务语义匹配"**——它代表"一次业务意图"，而不是"一条消息"。如果幂等键用消息 ID，那么消息重发（内容相同但 ID 不同）就不幂等了，这是常见错误。

**追问 2：幂等表会不会越来越大？**

**答**：会，所以有三种处理：① **短 TTL**（Redis 幂等键设过期，比如 24 小时，覆盖重试窗口）；② **按时间分区归档**（DB 幂等表定期清理）；③ **用业务唯一索引代替幂等表**（订单号唯一索引本身就是幂等表，不用额外维护）。

# 第 7 章 · 缓存与性能

### Q7.1 多级缓存是怎么设计的？🔴

**答**：用 **JetCache** 统一管理 **Caffeine（本地）+ Redis（远程）** 两级：
- **注解式**：`@Cached(expire=60min, localExpire=10min, cacheType=BOTH)` + `@CacheRefresh(refresh=50min)`；
- **作用范围**：热点藏品、盲盒、系列、用户；
- **配置**：JetCache 全局配本地 `caffeine`、远程 `redisson`，`defaultExpireInMillis: 5000`；Redisson 连接池 `connectionPoolSize: 64`、`threads: 16`、`nettyThreads: 32`。

读取顺序：**本地 → 远程 → DB**，任一层命中就返回；回填按需。

**追问 1：本地缓存和 Redis 的过期时间为什么不一样？（本地 10 分钟、远程 60 分钟）**

**答**：本地缓存**每台机器一份**，不一致的风险更高、更不可控，所以过期时间短（10 分钟）；远程缓存是全局共享的，过期时间可以长（60 分钟）。这样即使某个实例的本地缓存是旧值，最多 10 分钟也就回源了。
**代价要说清**：这仍然是**最终一致**——本地缓存和 Redis 之间、不同实例的本地缓存之间都可能短暂不一致，业务上必须能接受（藏品/用户信息可以接受，**库存不行**，所以库存不走这套）。

**追问 2：`@CacheRefresh` 和普通过期有什么区别？**

**答**：普通过期是"**懒加载**"——过期后第一个请求发现没命中，自己去查 DB 回填（回填期间其他请求都在等或穿透）；`@CacheRefresh` 是"**主动刷新**"——在过期前就定时去查一次 DB 把缓存更新掉。
好处是消灭了"过期瞬间的回源尖峰"（缓冲击穿）；**代价是每次都真的查库**，对于访问量很低的数据是纯浪费。所以它适合"**高频访问 + 允许短暂旧值**"的数据。

---

### Q7.2 缓存穿透、击穿、雪崩是什么？分别怎么解决？🔴

**答**：

| 问题 | 定义 | 解决 |
|---|---|---|
| **穿透** | 查询**不存在**的数据，缓存和 DB 都没有，每次都打 DB | ① **布隆过滤器**前置拦截（我项目里就用在昵称/邀请码判重）；② **缓存空值**（存 `null` 带短 TTL）；③ 参数校验 |
| **击穿** | **某个热点 key 过期**的瞬间，大量请求同时打到 DB | ① **互斥锁**（只放一个请求去查库，其余等待）；② **逻辑过期**（value 里存过期时间，后台异步刷新，前台返回旧值）；③ **主动刷新**（`@CacheRefresh`，我用的这个）；④ 热点 key **永不过期** |
| **雪崩** | **大量 key 同时过期**或**缓存服务整体宕机**，请求全部压到 DB | ① 过期时间**加随机抖动**（避免同时失效）；② **多级缓存**（本地缓存挡住一部分）；③ 缓存高可用（主从/集群）；④ **熔断降级**（Sentinel 限流 + 返回兜底数据）；⑤ DB 层限流保护 |

**追问：你项目里怎么防穿透？**

**答**：两条：① 布隆过滤器（用户注册相关）；② **售罄本地缓存**其实也是一种"穿透防护"——售罄的商品直接拒掉，连 Redis 都不查。

---

### Q7.3 Redis 为什么单线程还那么快？🔴

**答**：四个原因：
1. **纯内存操作**——没有磁盘 IO（除了持久化）；
2. **单线程避免了锁竞争和线程切换开销**——多线程抢同一份数据要加锁，上下文切换本身也是成本；单线程下所有命令天然串行，无锁；
3. **IO 多路复用**（epoll）——**一个线程管理大量连接**，哪个连接有数据就处理哪个，不需要为每个连接开线程（对比"一个连接一个线程"的 BIO 模型，连接数一多线程就爆了）；
4. **高效的数据结构**——SDS（动态字符串）、跳表、ziplist/listpack、渐进式 rehash，都为特定场景做了优化。

**追问 1：Redis 6.0 之后还是单线程吗？**

**答**：**命令执行仍是单线程**，但 **网络 IO 变成了多线程**（可以配 `io-threads`）。目的是把"读取请求、解析协议、写回响应"这些网络开销分摊出去，**核心的数据操作仍然串行**，所以不用担心并发安全问题。

**追问 2：多路复用和多线程什么区别？🔴**

**答**：
- **多路复用（IO multiplexing）**：**一个线程**同时监听多个 socket，用 `select/poll/epoll` 等待"哪个 fd 就绪"，就绪后依次处理。它是"**用一个线程处理多路 IO**"，节省的是线程资源。
- **多线程**：**多个线程**并行处理请求。它提升的是**并行度**（能同时用多核），代价是共享数据的锁竞争和上下文切换。
两者不冲突——现代服务常见组合是"多线程 + 每线程 epoll"（如 Nginx worker、Netty 的 EventLoop）。

**追问 3：epoll 比 select 好在哪？**

**答**：
- `select` 有 **fd 数量上限**（1024）且每次调用都要**把整个 fd 集合从用户态拷到内核态**，返回后还要**遍历所有 fd** 找就绪的——O(n)；
- `epoll` 用**内核中的红黑树**管理 fd（`epoll_ctl` 注册一次不用重复拷贝），就绪的 fd 由**内核直接放进就绪链表**（`epoll_wait` 直接返回就绪列表）——O(1) 级别的获取，适合高并发连接。

### Q7.4 Redis 的 key 会立即删除吗？🔴

**答**：**不会立即删除，是"惰性删除 + 定期删除"结合**：
1. **惰性删除（被动）**：key 过期后不会主动删，**等下次访问时**才检查是否过期，过期则删除并返回 nil；
2. **定期删除（主动）**：Redis 有一个定时任务（默认每秒 10 次），**随机抽取**一部分设置了过期时间的 key 检查并删除（不是全量扫描，避免卡顿）；
3. **内存淘汰（兜底）**：如果内存达到 `maxmemory`，按策略（`allkeys-lru` / `volatile-lru` / `allkeys-random` 等）淘汰。

**追问 1：为什么不全量扫描删除？**

**答**：单线程模型下，全量扫描会**长时间阻塞**服务（几百万个 key 扫一遍很慢）。所以用"抽样 + 惰性"的方式把删除成本分摊掉。

**追问 2：生产上为什么要禁用 `keys *`？**

**答**：`keys *` 会**遍历所有 key**，在单线程模型下会**阻塞整个 Redis**（几十万 key 就可能卡住几百毫秒甚至秒级）。生产上用 **`scan`** 做游标式遍历（分批返回、不阻塞，但可能重复/遗漏，需要业务容忍）。

### Q7.5 Redis 的部署方式？主节点挂了怎么办？🔴

**答**：三种常见形态：

| 形态 | 说明 | 故障处理 |
|---|---|---|
| **主从（replication）** | 一主多从，从节点只读、异步复制 | 主挂了**不能自动切换**，需要人工把从提升为主，期间写入不可用 |
| **哨兵（Sentinel）** | 在主从之上加**哨兵集群**（至少 3 个），监控 + 自动故障转移 + 通知客户端新主 | 哨兵判定主观下线（单哨兵）→ 客观下线（多数哨兵）→ 选举 leader 哨兵 → 提升某个从为主 → 客户端通过哨兵拿到新主地址 |
| **Cluster（分片集群）** | 数据按 **16384 个 slot** 分片到多个主节点，每个主带从 | 单个主挂了由其从节点自动接管；slot 迁移支持在线扩容 |

**追问 1：主从复制是同步还是异步？会丢数据吗？🔴**

**答**：**异步复制**。主节点写完内存就返回客户端，再异步把命令传给从节点。所以**主节点宕机时，那些还没同步到从的写会丢失** —— 这是"**Redis 主从无法保证强一致**"的根源，也是为什么**分布式锁在极端情况下可能丢锁**（Redlock 争议就来自这里）。
要减轻：用 `WAIT` 命令等待 N 个从确认（牺牲性能）、或者用 Redis 的 `min-replicas-to-write` 配置。

**追问 2：哨兵切换期间，客户端会出错吗？**

**答**：会。切换需要**几秒到几十秒**（判定下线 + 选举 + 提升 + 客户端刷新拓扑），期间：
- 写请求会失败（`READONLY You can't write against a read only replica` 或连接中断）；
- 客户端 SDK（Lettuce/Jedis）会重试并从哨兵重新获取拓扑。
所以**应用层必须能容忍短暂的 Redis 不可用**——这正是"降级"设计存在的原因。

**追问 3：你们项目用的哪种？**

**答**：项目里是单机/主从形态（开发环境用 Docker 起的单实例）。**要诚实说清生产该用哪种**：缓存场景推荐**哨兵或 Cluster**；但如果缓存里放了"库存"这种**不能丢**的数据（我项目就是），那么**缓存的高可用不能只靠 Redis 集群**，必须有"DB 为准 + 对账重建"的兜底——因为即使 Cluster 也可能整片不可用。

### Q7.6 热点 key / 大 key 怎么处理？

**答**：
- **热点 key**（某个 key 的 QPS 极高，比如爆款商品）：① **本地缓存**挡一层（我项目的售罄标记就是这个思路）；② **key 拆分**（`hotkey:1`、`hotkey:2`… 分散到不同节点）；③ **读写分离**（从节点分担读）；④ 如果是 Cluster，热点 key 会压在一个节点上，机器规格可以差异化。
- **大 key**（value 几 MB 的 String / 几万个成员的 Hash）：① **拆分**（大 Hash 拆成多个小 Hash）；② **不要用 `hgetall`/`keys` 类全量操作**（会阻塞）；③ **删除用 `unlink`**（异步删除，避免 `del` 阻塞主线程）。

**追问：怎么发现大 key / 热 key？**

**答**：① `redis-cli --bigkeys` 扫描；② `redis-cli --hotkeys`（基于 LFU）；③ **监控 + 采样**（客户端埋点统计 key 访问频率）；④ 阿里云/腾讯云的 Redis 控制台有专门的"热 key 分析"。

### Q7.7 项目里有哪些性能优化是真实做过的？

**答**：四个可以讲的（都有代码/配置依据）：
1. **库存扣减**：分布式锁的多轮 Redis 往返（加锁/读/扣/解锁）→ **单次 Lua**；DB 扣减从下单高峰**后移到支付后的低 QPS 阶段**；
2. **扫表 SQL**：`likeLeft('%xx')` 走不了索引 → **逆序冗余字段 `reverse_buyer_id` + 联合索引**，改成 `likeRight('xx%')`；同时从"单机串行"变成"**XXL-JOB 分片 + 多机并行**"；
3. **订单确认异步改同步**：压测发现异步处理让订单 CONFIRM 延迟变长，改回 `@TransactionalEventListener` **同步**调用（`OrderEventListener.java:24-25` 有注释原文）；
4. **搜索**：藏品同步走 **Canal + ES**，深分页用 **`search_after`**（避免 `from + size` 的深分页内存爆炸）。

**追问：第 3 条为什么异步反而更慢？**

**答**：异步把工作丢给了另一个线程池，看似"接口更快返回了"，但如果**下游线程池打满/排队**，事件实际处理的延迟被拉长；同时异步线程里的事务、上下文传递都更复杂。**压测数据说明：在这条链路上"同步"的整体完成时间更短**。这条经验的普适价值是——**不要凭直觉优化，要拿数据说话**。

# 第 8 章 · 场景设计题（架构师轮主战场）

> 这一章的题都是"**如果……怎么办**"。答题的通用框架是四段：
> **① 先给出判据**（这个场景的核心矛盾是什么）→ **② 说方案**（分步骤，含检测手段）→ **③ 说代价**（不吹）→ **④ 说兜底**（最坏情况怎么办）。
> 缺了 ③④ 就只是"背了篇博客"。

### Q8.1 秒杀过程中想临时加库存，你怎么办？🔴

**答**：先分清"**为什么加**"——① 运营想多卖（业务动作）；② 回滚补偿（技术动作）。两种处理不一样：
- **运营加库存**：走 `increase`（Lua 幂等 + 原子加 + 记流水），同时**清除售罄标记**（`soldOutGoodsLocalCache.invalidate`）。但要注意**本地缓存的多实例问题**——清了本机，其他机器的标记还在，会出现"部分用户仍被拒"。
- **补偿回滚**：同样的 `increase`，幂等号用**原扣减的 identifier**，避免重复回补。

**关键点**：项目的设计是"**秒杀进行中一般不允许加库存**"，因为售罄标记是本地缓存，**天生做不到秒级一致**。如果业务确实需要，正确姿势是**在秒杀开始前把库存配置到位**，或者接受"清标记后有一段秒级的拒绝窗口"。

---

### Q8.2 秒杀不引入 Redis、不用 Hint、也不用 MQ，只用数据库抗，有什么方案？🔴

**答**：这道题考的是"**没有缓存层时怎么解决热点行**"。四个方案：

| 方案 | 做法 | 代价 |
|---|---|---|
| **分桶（库存拆分）** | 1000 库存拆成 10 个桶各 100，用 `userId % 10` 路由到桶，各自扣减 | 桶间不平衡会**少卖**；要加桶间调配逻辑（复杂） |
| **拆成多条记录** | 同样的思路，把一行库存拆成 N 行，`UPDATE ... WHERE num > 0 LIMIT 1` 随机选一条 | 同上；且 N 行也要命中索引 |
| **串行化写入** | 应用内用**内存队列**（Disruptor/ArrayBlockingQueue）把扣减请求排队，单线程消费后写 DB | 单机吞吐上限；集群下要靠分片保证同一商品固定路由到同一实例 |
| **悲观锁 + 排队** | `select ... for update` 锁行，或者用**数据库的 `NOWAIT` / `SKIP LOCKED`**（MySQL 8.0）避免排队 | 吞吐低；`SKIP LOCKED` 会导致部分请求直接失败 |
| **异步落库** | 请求先入表（append-only），后台批量聚合扣减（把 N 次扣减合并成一次 UPDATE） | 一致性延迟；需要额外机制返回结果 |

**加分回答**：其实**数据库本身也有抗热点的能力**——阿里云 RDS 的 Inventory Hint（`COMMIT_ON_SUCCESS` / `ROLLBACK_ON_FAIL` / `TARGET_AFFECT_ROW`）就是官方为"抢购场景"提供的优化，让行锁冲突**快速失败而不排队**，减少锁等待造成的雪崩。**真正没法绕开的是"同一行的写必须串行"这个物理事实**——所有方案都是在"用不同方式降低串行化的粒度或时长"。

### Q8.3 Redis 挂了会怎样？怎么办？🔴

**答**：按数据分两类：

| 数据 | Redis 挂了的影响 | 应对 |
|---|---|---|
| **纯缓存**（藏品、用户信息） | 读请求全部落到 DB → **DB 可能被打垮** | ① 本地缓存（Caffeine）先挡一层；② 熔断限流（Sentinel）+ 返回兜底数据；③ **绝不能让请求无限制打到 DB** |
| **有状态数据**（库存、验证码、防重 token、限流计数、分布式锁） | **业务不可用**：无法安全判定剩余库存、无法校验验证码、无法防重 | **快速失败**——接口直接返回"系统繁忙/暂停服务"，**不要降级到查库扣库**（那等于把洪峰直接砸到 DB） |

**关键判断**：**"降级"不是"绕过"**。缓存类数据可以降级到 DB（因为 DB 是权威源）；而库存这类"唯一可卖掉数在 Redis 里"的数据，Redis 挂了就是**不可用**，硬降级会造成超卖。
**配套**：Redis 要**哨兵/Cluster 高可用** + 应用侧**降级开关** + **告警**（不能等用户来发现）。

**追问：那库存数据为什么不做成"DB 为准、Redis 只是加速"？**

**答**：如果 Redis 只是加速，那么"扣减的判定"回到 DB 就会撞上**热点行更新**的墙（见 Q8.2）——**高并发下 DB 根本扛不住把它当权威判定源**。所以是"用 Redis 的原子性换并发能力"，代价就是"Redis 是单点依赖，必须高可用 + 有重建方案"。

### Q8.4 MQ 挂了会怎样？怎么办？

**答**：分两个方向：
- **发消息失败**（Producer 侧）：下单链路里消息是在**本地事务回调**里发的，如果 Broker 不可用，`sendMessageInTransaction` 失败 → 本地事务状态是 UNKNOWN → **回查机制**在 Broker 恢复后会自动补偿。要确保 `checkLocalTransaction` 实现正确（根据本地流水判断该 commit 还是 rollback）。
- **消费停止**（Consumer 侧）：库存已扣、订单没建 → **用户看到"下单中"卡住**。应对：① 消费端恢复后按 offset 重放（消息没丢的话自动补齐）；② **兜底的定时任务**扫"长时间处于中间态的订单"，主动补建或回滚。

**关键点**：**MQ 不可用的最终兜底一定是"对账 + 补偿任务"**，因为消息可以做持久化但不能假设永远可用。
**要说的取舍**：也可以设计成"**双写**"（本地表 + MQ），本地表就是消息的持久化形态——这就是"本地消息表"方案，代价是多一次写和一套扫描逻辑。

### Q8.5 把 Redis 换成限流器可以吗？🔴（面试真题）

**答**：**不行，两者解决的不是同一个问题**。
- **限流器**回答的是"**要不要放这个请求进来**"——它控制的是**请求速率**，是"准入控制"；
- **Redis Lua 扣减**回答的是"**这单还能不能卖**"——它控制的是**资源的确切余量**，是"资源分配"。

举个反例：限流器设成"每秒放 100 个请求"，但库存只剩 3 件——**限流器会放 100 个进来，超卖 97 件**。反过来，库存还有 1000 件但限流器只放 10 个，就是**少卖**。
限流器和扣减是**互补**的：限流保护系统不被压垮，扣减保证不超卖。我的项目里两个都有（网关限流 + Lua 扣减）。

### Q8.6 线上数据库 CPU 100% 怎么排查？🔴

**答**：按"**从现象到根因**"的顺序：
1. **确认现象**：监控看到 CPU 100%（同时看 QPS、活跃连接数、慢查询数）；
2. **看当前在执行什么**：`show processlist`（或 `information_schema.processlist`）看有没有大量处于 `Sending data` / `Locked` 状态的 SQL；
3. **看慢查询**：`slow_query_log` + `pt-query-digest` 汇总出 TOP SQL；没有慢日志就开 `performance_schema`；
4. **看锁**：`show engine innodb status` 看有没有**锁等待**；`information_schema.innodb_trx` 看长事务；
5. **看执行计划**：对可疑 SQL 做 `EXPLAIN`，找**全表扫描**（type=ALL）、**filesort**、**临时表**；
6. **常见根因**：① 缺索引/索引失效（`like '%x'`、函数运算、隐式类型转换）；② **热点行更新**（秒杀打同一个库存行）；③ 长事务持有锁导致大量等待；④ 突然的流量涨（爬虫、活动）。

**追问：如果是"热点行"导致的呢？**

**答**：短期：**限流 + 屏蔽**超热商品；中期：把扣减**前移到 Redis**（我项目就是这么做的），或者把热点行**拆分**（分桶）；长期：DB 侧开 Inventory Hint 之类的针对性优化。**核心认知是：热点行更新在数据库层无解（必须串行），只能在架构上把它挪走。**

### Q8.7 接口 RT 突然升高，怎么排查？🔴

**答**：分**四层**往下切：
1. **入口层**：是全部接口慢还是个别接口？全部慢 → 网关/网络/依赖中间件；个别慢 → 定位到具体接口；
2. **应用层**：看**线程池/连接池状态**（打满就会排队）、GC 日志（是不是频繁 Full GC）、CPU 使用率；
3. **依赖层**：这个接口调了哪些下游（DB、Redis、Dubbo、MQ、第三方）？逐个看**调用耗时**（有链路追踪最好，我项目集成过 SkyWalking 类似的组件）；
4. **资源层**：DB 慢查询/锁等待、Redis 慢日志（`slowlog`）、网络抖动。

**追问：没有链路追踪怎么办？**

**答**：用"**二分法 + 埋点**"：① 在方法入口/出口打点记录耗时（先粗后细）；② 观察"是某个并发量以上才慢"还是"一直慢"——前者通常是资源竞争（锁/池），后者是逻辑问题；③ 临时降级某个下游看看是否恢复（比如把缓存开关打开）。

### Q8.8 慢 SQL 怎么定位和优化？🔴

**答**：
**定位**：开慢查询日志（阈值建议 100ms~1s）→ 用 `pt-query-digest` / `mysqldumpslow` 汇总 → 找出**出现次数最多 + 总耗时最长**的 SQL（不是单次最慢的）。
**优化**（按收益排序）：
1. **加/改索引**：让 `WHERE`、`JOIN`、`ORDER BY` 走索引；注意**最左前缀**、**不要对索引列做函数运算或前置通配**（我项目的 `likeLeft` 就是这个坑）；
2. **改写 SQL**：避免 `SELECT *`（利用覆盖索引）、避免 `OR`（拆成 `UNION`）、避免隐式类型转换（字符串列传数字会让索引失效）、**深分页改游标**；
3. **减少数据量**：分页、归档、分表；
4. **架构层**：读写分离、缓存、把统计类查询挪到 ES/OLAP。

**追问：怎么判断索引加得对不对？**

**答**：`EXPLAIN` 看 `type`（range/ref 以上）、`key`（用没用上）、`rows`（扫描行数）、`Extra`（避免 `Using filesort`/`Using temporary`）。**更实操的判据是"扫描行数是否接近返回行数"**——如果 `rows` 是 10 万而结果只有 10 行，说明索引没起效。

### Q8.9 MQ 消息堆积了怎么办？🔴

**答**：先**判断原因**，再对症：
1. **消费慢**（消费逻辑有慢查询/慢调用）→ 优化消费逻辑；**扩大并发消费**（RocketMQ 的消费并发度由队列数决定，可以先**增加队列数**再增加消费者实例）；
2. **消息生产暴增**（活动流量）→ 临时扩容消费者（但注意**消费者数不能超过队列数**，否则多的实例分不到队列）；
3. **消费异常反复重试** → 查是不是**某条毒消息**一直失败（会阻塞该队列）；定位后跳过/进死信；
4. **消费者实例挂了** → 重启，注意消费位点（保证没丢）。

**追问：堆积会有什么后果？**

**答**：① 消息延迟导致**业务超时**（下单很久没结果）；② Broker 磁盘/内存压力，严重时**拒绝写入**（新消息发不出去）；③ 如果开启了过期清理，**消息可能被丢弃**。

### Q8.10 全链路压测怎么做？

**答**：我项目只做过**单接口压测**（秒杀下单），全链路压测的完整方法是这样（要说清"我没做过但知道怎么做"）：
1. **目标是找瓶颈**：从最外层入口压，逐层往下看每一层的 RT 和资源；
2. **数据隔离**：用**影子表/影子库**或者**流量标记**，避免压测数据污染生产（RocketMQ 消息打标、DB 写影子表、缓存用独立前缀）；
3. **流量构造**：按线上真实比例构造请求（读多写少、有热点）；
4. **逐级加压**：找到**拐点**（QPS 上升但 RT 陡增的那个点就是瓶颈）；
5. **观测**：每层的 RT、错误率、CPU/内存/连接池/GC、MQ 堆积、DB 慢查询；
6. **定位与优化后再压**，对比数据。

**追问：压测最常暴露的问题是什么？**

**答**：① **连接池不够**（DB/Redis/HTTP 连接打满）；② **线程池不够**（任务排队）；③ **GC 频繁**（对象创建过多）；④ **慢 SQL**；⑤ **单点**（某个服务实例成瓶颈）。

### Q8.11 如果流量再涨 10 倍，你怎么办？🔴

**答**：按"**先扛住、再优化、后重构**"分层回答：

**架构层（成本最低，先做）**：
- **水平扩容**：无状态服务加实例（网关、业务服务）；
- **限流**：网关 + 应用双层限流，**保住核心链路**（下单、支付），牺牲非核心（推荐、排行榜）；
- **降级**：关掉非核心功能（图鉴、评论），把资源让给交易；
- **缓存**：把更多读请求挡在缓存层。

**数据层**：
- 库存继续用 Redis（本来就在）；
- **分库分表扩容**（从 4 张到 8/16 张，需要数据迁移 + 双规则路由）；
- 读多写少的走**读写分离**或 ES。

**链路层**：
- MQ 扩队列 + 扩消费者；
- 秒杀**独立部署**（隔离资源，不让秒杀把主站拖垮）；
- 热点商品**独立分片/独立集群**。

**要说的话**：**"10 倍流量"不是单点优化能解决的，是一个"容量规划 + 隔离 + 降级"的组合工程**，而且要先想清楚**哪些业务可以牺牲**。

### Q8.12 怎么设计一个通用的幂等框架？

**答**：核心是"**幂等键 + 存储 + 拦截**"三件套：

```java
@Idempotent(key = "#request.orderNo", expire = 24, timeUnit = HOURS)
public Result createOrder(OrderRequest request) { ... }
```

1. **幂等键**：用 SpEL 从方法参数提取（如订单号、token），或者由业务显式传入；
2. **存储**：Redis `setnx(key, requestId, expire)` —— **必须原子**（用 `SET NX EX` 或 Lua），且**在方法执行前占位、执行后保留**（保留期覆盖重试窗口）；失败时**要能区分"正在执行"和"已执行成功"**（value 里存状态：`PROCESSING` / `SUCCESS`+结果）；
3. **拦截**：AOP 切面，执行前占位，执行后更新状态；
4. **兜底**：DB 唯一索引（框架不可靠时的最后防线）。

**追问：`setnx` 占位后业务执行失败了，键要删吗？**

**答**：要，而且这是个坑——
- 如果**执行失败**就删掉键，那么"重试"能正常进行；
- 但如果**执行成功**还没返回时进程挂了，键留在 `PROCESSING`，下次请求会被拒——所以要有"**处理中状态的超时**"（比如 30 秒后允许重试）；
- 更稳的做法是**把结果也存进去**：`SUCCESS` 时直接返回缓存的结果（真正的幂等语义），`PROCESSING` 时返回"处理中请稍候"。

### Q8.13 秒杀活动要预热吗？怎么预热？

**答**：要。预热内容：
1. **库存进 Redis**：活动开始前把库存写进 Redis（`init`），避免第一个请求才发现 key 不存在；
2. **商品信息进缓存**：详情页数据提前进本地 + Redis，避免开抢瞬间大量请求回源 DB；
3. **售罄标记复位**：确保没有残留的售罄标记拦掉正常请求；
4. **限流/降级规则下发**；
5. **容量准备**：扩容实例、MQ 队列、连接池调优；
6. **压测验证**：活动前做一次小规模压测确认。
7. （进阶）**提前下发静态资源 + 前端页面静态化/CDN**，把详情页的静态部分完全挡在服务端之外。

**追问：预热时要注意什么？**

**答**：**幂等**——预热的脚本可能被执行多次，`init` 要判断 key 是否已存在（项目里的 `init` 就是先 `isExists` 再 `set`，命中则返回 `DUPLICATED`）。

### Q8.14 怎么发现超卖或少卖？🔴

**答**：靠**对账**，而不是靠"相信代码"：
1. **超卖的检测**：`DB 已售数量 + Redis 剩余量 ≤ 初始库存`（恒等式）。任意时刻这个不成立就告警；
2. **少卖的检测**：活动结束/库存清零后，`DB 已售 < 初始库存` 且 `Redis 还有剩余` 就是少卖；
3. **逐笔对账**：Redis 的**扣减流水**（保留 24 小时）与 DB 的订单/库存变动记录**逐笔比对**：流水里有但 DB 里没有 → 少卖（预占没释放）；DB 里有但流水里没有 → 可能是重复扣或绕过 Redis 的操作；
4. **不一致处理**：记入 `mismatch` 表，告警 + 人工/自动修复（`nft-turbo-check` 模块负责这块）。

**关键点**：**能检测**比"保证不发生"更重要——任何分布式方案都有极端情况，**有对账就有兜底**。

### Q8.15 分布式锁失效了怎么办？

**答**：先分类：
- **锁超时提前释放**（业务耗时超过租期）：用**看门狗自动续期**（Redisson 不指定 leaseTime 时默认开启）；
- **主从切换丢锁**：Redis 异步复制导致锁只在主上，切主后锁没了 → 用 **Redlock**（向多数节点加锁，多节点确认）或 **ZooKeeper**（临时顺序节点，强一致）；
- **锁被误解**：value 存持有者标识，用 Lua 比较后删除（Redisson 已做）。

**但根本上**：**分布式锁只能降低并发冲突的概率，不能替代"业务层的幂等与约束"**。所以真正的安全网是 **DB 唯一索引 / 状态 CAS / 幂等键** —— 即使锁失效，也不会产生错误数据（最多是并发冲突被后续约束拦住）。**这是我设计时的一贯原则：锁是优化，约束才是正确性。**

### Q8.16 怎么保证"缓存和数据库"最终一致？不一致了怎么发现？

**答**：
- **预防**：Cache Aside（先更库再删缓存）+ 延迟双删 + 短 TTL + 主动刷新；
- **发现**：① **监控缓存命中率异常下降**（说明数据在反复失效）；② **抽样比对**（定时任务抽样查缓存和 DB，比对不一致率）；③ 业务侧的对账任务（如库存、订单状态）；
- **修复**：以 DB 为准，**删除/覆盖缓存**（不要"改缓存"，因为改缓存解决不了"多张表拼出来的缓存值"）；严重时**全量重建**。

### Q8.17 线上应用 CPU 飙高怎么排查？🔴

**答**：六步：
1. **确认是哪个进程**：`top` 找到高 CPU 的 Java 进程；
2. **定位线程**：`top -Hp <pid>` 找到高 CPU 的线程 ID，转成十六进制；
3. **看线程栈**：`jstack <pid> | grep -A 30 <nid>` 找到这个线程在干什么；
4. **归类常见原因**：
   - **死循环 / 无限重试**（业务代码 while 没有退出条件、正则回溯）；
   - **频繁 Full GC**（内存泄漏或堆太小）→ 看 `jstat -gcutil` 和 GC 日志；
   - **大量计算**（序列化/反序列化大对象、正则、加解密）；
   - **锁自旋 / 大量线程上下文切换** → `vmstat` 看 `cs`（上下文切换次数）；
5. **看火焰图**（`async-profiler` / Arthas `profiler`）定位到具体方法；
6. **临时止血**：降级、重启、扩容；**根治**：改代码。

**追问：如果 CPU 不高但接口很慢呢？**

**答**：那是**等待型问题**——`jstack` 看线程都在等什么（`WAITING` / `BLOCKED`）。常见：**DB 慢查询**、**下游接口慢**、**锁等待**、**连接池/线程池排队**、**GC 停顿**（看 GC 日志里的 STW 时间）。

### Q8.18 内存泄漏 / OOM 怎么排查？🔴

**答**：
1. **确认现象**：`jstat -gcutil <pid> 1000` 看老年代是否**持续增长且 Full GC 后不下降**（这才是泄漏；如果 Full GC 后能降下来只是"内存不够/对象太多"）；
2. **拿快照**：`jmap -dump:live,format=b,file=heap.hprof <pid>`，或者 OOM 时配置 `-XX:+HeapDumpOnOutOfMemoryError` 自动 dump；
3. **分析**：MAT / VisualVM 看**支配树（Dominator Tree）**和"最大的对象/引用链"，找到谁在持有；
4. **常见泄漏源**：**`ThreadLocal` 没 remove**（线程池场景下线程复用，value 一直挂着）、静态集合无上限增长、缓存没设上限（本地缓存必须有容量限制，Caffeine 默认有）、连接/流未关闭、监听器注册未注销。
5. **修复后验证**：压测跑一段时间，看老年代是否稳定。

**追问：为什么 ThreadLocal 会内存泄漏？🔴**

**答**：`ThreadLocalMap` 的 key 是**弱引用**（`WeakReference<ThreadLocal>`），value 是**强引用**。当 ThreadLocal 对象被回收后，key 变成 null，但 **value 仍然被 Entry 强引用**，只要线程还活着（**线程池里的线程长期存活**），这个 value 就永远回收不掉 —— 这就泄漏了。
**而且**：ThreadLocalMap 使用线性探测，key 为 null 的 Entry 会让探测链变长，还可能导致后续 put 触发的 rehash/清理不及。
**解决**：**用完必须 `remove()`**（放在 `try-finally` 里）；线程池场景尤其重要。JDK 在 `get/set/expungeStaleEntry` 时会顺便清理一部分 stale entry，但这只是"顺手"，不能依赖。

### Q8.19 用户投诉"我付了钱但没拿到藏品"，你怎么查？🔴

**答**：按**业务链路的顺序**逐环节核对：
1. **支付**：查支付单——有没有这一笔？状态是否 `已支付`？第三方流水号是多少（拿它去微信商户平台核对是否真的到账）？
2. **订单**：订单状态是 `已支付` 还是 `已关闭`？**如果是已关闭 → 说明发生了"支付成功但订单被关"的竞态**，那答案就是"钱会退给你"，并检查退款单是否已生成；
3. **库存**：DB 库存有没有扣？Redis 流水里有没有这笔扣减？
4. **持有藏品**：`held_collection` 有没有这个用户的记录？状态是 `铸造中` 还是 `成功`？
5. **上链**：链上操作记录（`ChainOperateStateEnum`）处于什么状态？是不是在重试队列里？
6. **日志**：按订单号/支付单号把全链路日志串起来（有 traceId 最好）看哪一步断的。

**结论处理**：① 在重试队列里 → 等重试或手动触发；② 链上失败且重试耗尽 → 告警 + 人工介入补铸；③ 确认重复扣款/订单已关 → 退款。
**这题的关键不是"能查"，而是体现出你知道"这条链路有 6 个可能断的地方，每个地方都有对应的可观测性"**。

### Q8.20 支付回调乱序（先收到"支付中"、再收到"失败"、又收到"成功"）怎么办？

**答**：
1. **不信任到达顺序**，只信任**终态判定**——每条回调都当作"一次状态查询的结果"，用状态机 + CAS 决定是否推进（`WHERE lock_version = ? AND state = ?`）；
2. **同一状态重复到达** → 幂等返回（`if (isPaid()) return true`）；
3. **矛盾状态**（已经"成功"了又来"失败"）→ **以资金事实为准**：主动调第三方的**查询接口**确认真实状态，而不是用回调的先后顺序判断；
4. **乱序导致的业务动作**：比如"失败"回调先到，把订单关了；"成功"回调后到 → 触发**退款 + 告警**（项目里的重复支付/已关单退款场景）；
5. **兜底**：定时对账（T+1 拉账单）。

**核心原则**：**外部事件的到达顺序不可信，状态机 + 权威查询才是真相**。

### Q8.21 怎么防黄牛 / 脚本刷接口？🔴

**答**：分层设防，从"能不能进"到"能不能买"：
1. **网关层**：IP/用户维度**限流**、黑名单、设备指纹；
2. **认证层**：必须登录 + 实名（项目里 `/trade/**` 需要 `AUTH` 权限）——提高黄牛的账号成本；
3. **业务层**：
   - **限购**（每人 N 件，Redis 计数）；
   - **一次性 token**（必须从详情页拿到，脚本无法凭空构造）；
   - **活动时间窗**（未开始/已结束直接拒）；
   - **风控规则**（同一收货地址/设备/支付账号关联多个账号）；
4. **验证码/滑块**（高频请求时触发人机校验）；
5. **前端不可信**，所有校验服务端重做一遍。

**追问：这些东西会不会误伤正常用户？**

**答**：会，所以要有**降级开关 + 灰度**：风控规则上线先"只记录不拦截"（观察误伤率），确认后再开启拦截；验证码只在检测到异常频率时才弹。**风控的难点从来不是"拦得住"，而是"既拦得住又不误伤"。**

### Q8.22 大促前你会做什么准备？

**答**：一张检查清单：
- **容量**：压测找拐点 → 按预期的 1.5~2 倍扩容（应用实例、DB 连接、Redis 连接池、MQ 队列/消费者、线程池）；

- **监控告警**：核心指标（QPS、RT、错误率、库存、MQ 堆积、DB 慢查询、GC）阈值告警 + **大盘**；
- **应急预案**：回滚方案（灰度/蓝绿）、紧急扩容脚本、库存修正脚本准备；

**追问：如果活动开始后发现库存超卖了，你怎么办？**

**答**：**先止血再追责**：① 立即**下架/暂停售卖**该商品；② 评估超卖数量；③ **与超卖用户协商**（补货/退款/补偿）；④ 事后定位根因（幂等失效？对账没跑？加库存绕过 Redis？）。**技术侧的第一动作永远是"停止损失扩大"，不是"现场 debug"。**

### Q8.23 灰度发布怎么做？出问题怎么回滚？

**答**：
- **灰度策略**：按**流量比例**（1% → 10% → 50% → 100%）、按**用户维度**（白名单/用户 ID 取模）、按**机器维度**（先发一台）；网关层做路由分流；
- **观测指标**：新版本的错误率、RT、异常日志与老版本对比，有差异立即停；
- **回滚**：**镜像回滚**（保留上一个版本的镜像，最快）；数据库变更要**向前兼容**（加字段而不是改字段，避免回滚后旧代码读不到新字段）；
- **注意**：灰度期间**新旧版本要能共存**（API/数据结构兼容），否则没法回滚。

**追问：数据库变更怎么做到可回滚？**

**答**：**扩展-收缩模式**（expand-contract）：① 先**加新字段/新表**（不删旧的），双写；② 数据迁移/双读校验；③ 切换读；④ 确认无误后再删旧字段。任何一步都可以回退。

### Q8.24 单机 QPS 300 想提到 3000，怎么做？🔴

**答**：先找**瓶颈在哪**，再对症：
1. **如果瓶颈在 Redis 网络往返**：用 **pipeline / 批量**、减少调用次数（我项目已经用 Lua 把 4 次往返压成 1 次）；
2. **如果瓶颈在应用 CPU**：异步化、减少对象创建、减少序列化开销、jstack/火焰图找热点方法；
3. **如果瓶颈在 DB**：把同步 DB 操作挪到异步（我项目的做法）、读写分离、加缓存；
4. **如果瓶颈在锁/线程池**：减少临界区、提高并发度、**避免长事务**；
5. **最直接的手段是水平扩容**（加机器），但要说清"**先找出瓶颈再扩，否则扩了也没用**"——如果瓶颈在 DB 单点，加应用实例只是把压力更均匀地打在 DB 上。

**追问：怎么知道瓶颈在哪？**

**答**：**逐步加压 + 观察各层指标**。压到某个 QPS 后 RT 陡增，看那一刻**哪个资源先到饱和**（CPU、DB 连接、Redis 连接、GC、MQ），那就是瓶颈。这就是"**压测找拐点**"。

### Q8.25 现场设计：从零设计一个秒杀系统（白板题）🔴

**答**：按四层讲：
1. **接入层**：CDN 静态化详情页 → 网关限流（IP/用户维度）→ **活动开始前**把"未开始/已结束"的请求直接挡掉；
2. **应用层**：
   - **前置校验**（状态、实名、限购）；
   - **一次性 token 防重**；
   - **Redis Lua 原子扣减**（幂等 + 判断 + 扣减 + 流水）；
   - **售罄本地标记**快速失败；
   - **异步下单**（MQ 削峰，消费端幂等建单）；
3. **数据层**：库存以 Redis 为准、DB 为账本；订单分库分表；DB 侧原子扣减 + 避免热点；
4. **兜底**：MQ 重试 + 延迟补偿 + 定时对账 + 库存重建方案。

**加分点（主动说）**：
- **秒杀独立部署**（不与主站共享资源）；
- **热点商品单独特判**（独立分片、独立缓存）；
- **每层都要能降级**；
- **库存的"预扣 - 确认 - 取消"三段式**（我项目里的 Lua 是预扣，DB 扣减在支付后确认）。

### Q8.26 现场设计：藏品转让（二级市场）怎么做？

**答**：这是数藏项目的特色题：
1. **权益归属**：转让的是**持有记录**（`held_collection`）的 owner，不是数据库里的商品；
2. **上链**：转让要让链上所有权变更，所以要走 `transfer` 链操作，**链上成功才是真的转让成功**；
3. **冻结**：挂单期间藏品要**冻结**（不能同时转让给两个人）——项目里库存模型有 `freezeInventory` / `unfreezeInventory`，思路一致；
4. **一致性**：交易、订单、藏品、链上多处变更 → 参考支付链路：核心几步用 AT，上链走事务钩子 + 重试；
5. **资金**：买家付钱、卖家收款 → 涉及**分账/结算**和平台抽成，资金流要有独立流水；
6. **风控**：限价、防刷、防自买自卖。

**追问：链上转让失败但钱已经付了怎么办？**

**答**：同支付链路的选择——**钱不能回滚**，所以藏品归属必须"挂起 + 重试"，重试耗尽则**告警 + 人工介入或退款**。**绝不能因为链上失败就把已收的钱退回去当作没发生**（除非业务明确"链上失败就退款"，那也要作为一条显式流程，而不是异常处理）。

### Q8.27 时间/时区问题你踩过哪些坑？

**答**：项目里踩过一个具体的：**订单详情页倒计时显示 NaN** —— 后端 `payExpireTime` 是 `java.util.Date`，Spring Boot 3 默认用 Jackson 序列化成 **ISO 8601 字符串**，前端直接拿字符串做减法得到 `NaN`，而且 `NaN <= 0` 是 false，兜底判断也失效。
**通用教训**：
1. **跨端传输时间统一用时间戳（毫秒数）或明确的 ISO 8601 带时区**，前端拿到字符串必须显式 `new Date()` 解析；
2. **`java.util.Date` 已经过时**，新代码用 `LocalDateTime` / `Instant` + 明确的 `@JsonFormat(pattern, timezone)`；
3. **服务器时区**要统一（容器里默认是 UTC，和数据库、日志的时区不一致会导致"时间差 8 小时"的诡异问题）；
4. **数据库存时间用 `datetime`/`timestamp` 要看语义**（`timestamp` 会随时区转换，`datetime` 不会）。

### Q8.28 库存扣了但订单没生成，怎么发现、怎么处理？

**答**：
- **发现**：① 监控"**预扣库存总量 vs 订单总量**"的差值（差值持续变大就是在漏）；② 对账任务比对 Redis 流水与订单表；
- **处理**：① 找出没有对应订单的流水（幂等键在流水里）；② **回补库存**（用同一个 identifier 调 `increase`，天然幂等）；③ 如果是因为 MQ 丢消息导致的，同时检查消息链路的可靠性配置；
- **预防**：MQ 事务消息 + 消费端幂等 + 定时补偿任务（延迟消息回滚）+ 对账。

### Q8.29 怎么保证"一个用户只能买一件"？

**答**：三道锁：
1. **Redis 计数**：`setnx` 一个 `限购:商品ID:用户ID`，成功才放行（**带上活动结束的 TTL**）——这是最外层、最快的拦截；
2. **数据库唯一索引**：`(商品ID, 用户ID)` 唯一（或订单表上加"限购标识"），这是**最终权威**；
3. **业务校验**：下单前查该用户对该商品的已购数量。
**为什么三道都要**：Redis 是缓存可能丢；DB 唯一索引是权威但慢；业务校验是兜底和给用户友好提示。**"限购"和"防重"是两个不同的问题**——防重防的是"同一个请求重复提交"，限购防的是"用户想买第二件"。

### Q8.30 对外提供开放接口，怎么防重放/防篡改？

**答**：
1. **签名**：请求参数 + 时间戳 + 随机数（nonce）+ 密钥 → HMAC 签名，服务端验签（防篡改）；
2. **时间戳窗口**：超过 ±5 分钟的请求直接拒（防旧请求重放）；
3. **nonce 去重**：`setnx(nonce)` 在 Redis 里存窗口期（防同一请求重复使用）；
4. **幂等**：业务侧对"业务唯一键"做幂等（防同一笔业务被重复处理）；
5. **HTTPS + 密钥管理**（AppSecret 不能放前端）。

### Q8.31 如果让你重新设计订单分表，你会改什么？🔴

**答**：三个反思：
1. **分片键**：买家 ID 对"买家查订单"最优，但**卖家/后台维度的查询必须走 ES 或冗余表**。如果重来，我会**在建表时就规划一张"卖家维度索引表"**（或明确把卖家查询全部导向 ES），而不是事后补；
2. **基因法的可扩展性**：把"表下标"编进订单号，扩容时老数据要双规则路由。如果预见到增长，**订单号里保留的表下标位数应该更宽**，或者干脆**不在订单号里编下标、改用"订单号 → 分片映射表"**（代价是一次额外查询）；
3. **分库时机**：一开始就分表不分库是合理的（成本低），但**要提前把"分库"作为既定路线**（如数据源抽象、路由层可配置），避免真到分库时大改。

**追问：如果现在订单量翻 10 倍要扩到 16 张表，怎么迁移？**

**答**：**双写 + 渐进迁移**：
1. 建新表（16 张）；
2. **双写**（新老表都写）——或者按"订单 ID 范围/时间"切分，新订单写新表，老订单留在老表；
3. **后台迁移**老数据（分批，避免影响线上）；
4. **双读**（先读新表，miss 再读老表）校验；
5. 校验完成后**切换读写到新规则**，老表归档；
6. 全程可回滚（老表在切换完成前不删）。

### Q8.32 怎么设计一个"对账"任务？

**答**：对账的本质是"**用两个独立的数据源交叉验证同一件事实**"：
1. **对账对象**：本项目里是"本地支付单 ↔ 微信账单"、"Redis 库存流水 ↔ DB 库存扣减记录"、"订单状态 ↔ 支付单状态"；
2. **流程**：拉取外部数据（T+1 账单）→ 按业务单号关联 → 逐笔比对状态/金额 → **差异落 `mismatch` 表**；
3. **差异分类处理**：
   - **本地有、外部没有** → 可能是本地多记（要冲正）；
   - **外部有、本地没有** → 可能是回调丢失（要补单/退款）；
   - **状态/金额不一致** → 以**外部资金侧为准**，修正本地；
4. **告警 + 人工介入**：不一致超过阈值告警，重要的（涉及资金）必须人工确认，不能自动改。
5. **幂等**：对账任务本身要可重复执行（对同一天的账单重复跑不会重复处理）。

**关键点**：**对账是最后一道防线，也是"允许前面放宽一致性"的前提**——没有对账，任何最终一致的方案都是裸奔。
